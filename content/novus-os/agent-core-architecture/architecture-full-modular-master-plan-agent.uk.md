# ПОВНИЙ МОДУЛЬНИЙ МАСТЕР-ПЛАН — AGENT CORE (КАНОНІЧНИЙ SSoT)

Статус: ЗАВЕРШЕНО ТА ЗАФІКСОВАНО (Базова версія v0.2.0, 2026-09-25)

Область застосування: лише agent-core, з дотриманням міжрепозиторних меж щодо panel-core та installer.

Нормативні прив'язки:
- AGENTS.md
- ECOSYSTEM_MANIFEST.md

Цей файл замінює планування операційного розділення як авторитетний мастер-план.
Робочі артефакти в docs/dev залишаються допоміжними записами, а не паралельним джерелом істини.

## 0. Місія, область застосування та безкомпромісні обмеження

Місія:
- Розвинути agent-core у модульне, орієнтоване на безпеку Go-середовище виконання корпоративного рівня зі збереженням сумісності з платформою та транспортних контрактів.

Безкомпромісні обмеження:
- Відсутність критичного дрейфу контрактів gRPC під час міграції.
- Заходи безпеки залишаються чинними наскрізно (TLS, підписані метадані, replay, rate limit, аудит).
- Жодної втрати бізнес-можливостей для телеметрії, операцій середовища виконання, VFS, резервного копіювання, PTY, консолі WebSocket, SSH/SFTP.
- Детерміновані фазові переходи з відтворюваною валідацією.
- Збереження взаємодії з Installer та Panel у різних релізах.

## 1. Авторитетні інваріанти продукту та контрактів

## 1.1 Поверхня API та усунення дрейфу контрактів

Авторитетне рішення:
- BackupService та ReinstallInstance залишаються офіційною поверхнею gRPC-контракту платформи.

Обов'язковий інваріант:
- Джерело контракту в proto/novus.proto, згенеровані заглушки та реєстрація у середовищі виконання розглядаються як неподільна базова лінія.

Забезпечення виконання:
- Тест захисту від дрейфу контрактів є обов'язковим у CI та локальних гейтах.
- Будь-яке додавання або видалення сервісу/методу вимагає узгоджених змін у вихідному контрактi, згенерованому коді, обробниках, тестах, документації та послідовності релізу.

## 1.2 Інваріанти зміцнення транспорту (WebSocket та SSH)

Авторитетне рішення:
- WebSocket та SSH залишаються увімкненими за замовчуванням.

Обов'язкові вимоги до зміцнення:
- WebSocket:
  - Видалити поведінку CheckOrigin з використанням підстановочних знаків (wildcard).
  - Забезпечити сувору валідацію JWT-клеймів, прив'язану до контексту вузла, контейнера та сесії.
- SSH/SFTP:
  - Ключ хоста має бути постійним і генеруватися один раз.
  - Зберігати ключ за захищеним шляхом стану хоста (/etc/novus-agent/ або відповідно до політики шляху стану, узгодженої з життєвим циклом NOVUS_AGENT_STATE_FILE).
  - Видалити захардкоджений :2022 із завантажувача середовища виконання та перенести до конфігурації.
  - Маршрутизувати доступ до диска через SFTP через єдиний VFS Policy Engine.
  - Вимагати канонікалізації за допомогою filepath.EvalSymlinks перед усіма фактичними операціями з файловою системою.

## 1.3 Інваріант архітектури VFS: Контекстно-залежний рушій політик OIM/IAM

Архітектура VFS має еволюціонувати від бінарного вибору області видимості (scope) до гранульованого опрацювання політик.

Обов'язкові режими політик:
- Режим host_admin:
  - Повний доступ до файлової системи хоста для довірених процесів адміністрування вузлів.
- Режим scoped_runtime:
  - Базова ізоляція тенанта/середовища виконання до кореневих каталогів /var/lib/novus/volumes/*.

Обов'язкові можливості гранульованого захисту OIM/IAM на рівні шляхів:
- AllowedSubpaths:
  - Позитивний білий список (allowlist) конкретних піддерев усередині томів середовища виконання.
- HiddenPaths та MaskedPaths:
  - Заборона видимості в списках каталогів та відповідях з метаданими для захищених шляхів.
- AccessFlags:
  - Прапори операцій на рівні шляхів: Read, Write, Delete, Chmod.
- Symlink-Traverse Guard:
  - Канонікалізація через filepath.EvalSymlinks з подальшою перевіркою кінцевої цілі на відповідність маскам та прапорам політики.

Інваріант межі:
- Agent забезпечує дотримання технічної області видимості та виконання захисту шляхів; Panel залишається органом прийняття рішень IAM/OIM.

## 1.4 Інваріант бінарного конвеєра оновлення (P0)

Обов'язкова поведінка:
- Повне видалення виконання оновлень на основі скриптів (curl | bash заборонено).
- Конвеєр оновлення має керуватися бінарним файлом:
  - отримання метаданих релізу через GitHub Releases API,
  - завантаження артефакту Linux ELF,
  - перевірка необхідної контрольної суми SHA-256,
  - виконання атомарної заміни бінарного файлу через os.Rename,
  - перезапуск юніта за контрольованою політикою з можливістю відкочування у разі невдалої активації.

## 2. Повний звіт про аудит (консолідований)

## 2.1 Критичні виявлені проблеми

1) Небезпечний шлях виконання оновлювача (updater).
- Докази: internal/grpcserver/service.go (шлях UpdateAgent, який викликає конвеєр shell-скриптів).
- Ризик: вразливість ланцюга постачання / RCE.

2) Історичний ризик дрейфу контракту (наразі узгоджений у вихідному контрактi та документації, захист збережено).
- Контекст доказів: розходження між реєстрацією в runtime та вихідним proto до узгодження.
- Ризик: несумісність панелі/агента та невідтворюваність генерації protobuf.

3) Прогалина в посиленні захисту WebSocket origin та claim.
- Докази: прийняття wildcard origin та недостатня прив'язка контексту.
- Ризик: cross-origin / несанкціоноване використання токенів у транспорті сумісності.

## 2.2 Виявлені проблеми високого рівня

1) Перевірка шляхів SFTP обходить уніфікований шлях політики VFS.
- Докази: прямі операції os.* у шляху адаптера SFTP.
- Ризик: неузгоджена поведінка ізоляції та вразливість до обходу символьних посилань (symlink traversal).

2) Область видимості VFS середовища виконання за замовчуванням відповідає кореню всієї хост-системи.
- Докази: під час bootstrap AllowedRoots встановлено у /.
- Ризик: ізоляція тенантів на рівні контексту ще не забезпечується за замовчуванням режимом політики середовища виконання.

3) Життєвий цикл ідентичності SSH-хоста та технічний борг у налаштуванні.
- Докази: непостійний життєвий цикл ключа хоста та жорстко закодований порт SSH у шляху bootstrap.

## 2.3 Виявлені проблеми середнього рівня

1) Невикористовувані або слабко інтегровані шляхи.
- Інтеграція обробника команд та оркестрації планувальника потребує явного визначення власника та очищення життєвого циклу.

2) Розходження документації (частково усунено).
- Ключі конфігурації та заявлена поведінка мають постійно відповідати реальності середовища виконання.

3) Невідповідність щільності покриття тестами для поверхонь із високим рівнем ризику.
- Шляхи, критичні для транспорту та безпеки, потребують більш глибокого та фокусованого тестування.

## 4. Стандарт управління документацією (суворий)

Документація повинна розвиватися синхронно з архітектурою та реалізацією.

Обов'язкові контури документації:

1) Контур розробника (docs/development/):
- внутрішній устрій модулів, розширення поверхонь gRPC, контракти типів,
  поведінка протоколу панель-агент, стандарти тестування, перевірки відповідності (fitness controls).

2) Контур оператора та системного адміністратора (docs/ public operator set):
- конфігурація середовища, відкриті порти, налаштування systemd,
  модель стійкості SSH/TLS, стан безпеки, мережева ізоляція, діагностика.

3) Користувацький/довідковий контур (docs/ public reference set):
- довідник змінних середовища, ліміти/можливості VFS,
  функціональні довідники SFTP та вебконсолі.

4) Внутрішній інженерний контур (docs/dev/):
- приватні аудити, реєстри технічного боргу, трекери виконання, примітки щодо міграції.

Вимога щодо санітизації даних безпеки:

- Публічна документація має залишатися максимально функціональною, але забезпечувати нульове розголошення ланцюжків експлойтів, шляхів до секретів приватних хостів, інструкцій із обходу або деталей наступальних операцій.

## 7. Безперервна еволюція: Антимонолітний модульний інваріант
Усі подальші доопрацювання ядра агента підпорядковуються правилу нульової монолітної експансії (Zero-Monolith Policy):   
1) Заборона на розширення спільних та кореневих шарів: Заборонено додавати бізнес-логіку в internal/grpcserver, main.go, спільні хелпери або платформенні пакети internal/platform/*.   
2) Маршрутизація функціоналу (Domain Routing):
  - Існуючий домен: Якщо задача стосується існуючої функціональності (InstanceLifecycle, RuntimeSurface, FilesVFS, UpdateManager тощо), реалізація ведеться виключно всередині відповідного модуля (internal/modules/<Domain>/...).
  - Новий домен: Якщо задача представляє новий незалежний контекст (наприклад, HypervisorKVM, MetricsEngine, TelemetryUDP), вона оформлюється суворо як новий автономний модуль за канонічним стандартом (application, domain, infrastructure, transport).   
3) Слабка зв'язаність (Loose Coupling): Міжмодульна взаємодія дозволена тільки через публічні інтерфейси портів, шину подій або типізовані контракти без циклічних та інфраструктурних імпортів.

## 8. Визначення завершеності

Завершення програми вимагає закриття всіх контрольних точок і виконання всіх наведених нижче умов:
- сервіси runtime декомпоновані до запланованих меж модулів,
- відсутні критичні невирішені прогалини в оновлювачі, рушії політик VFS або ідентичності SSH-хоста,
- збережено сумісність gRPC/API для інтеграцій Panel та Installer,
- застарілу оркестрацію зведено до тонких транспортних прошарків (shims),
- документацію синхронізовано з поведінкою runtime для всіх необхідних аудиторій,
- усі гейти якості та готовності до релізу є «зеленими».
