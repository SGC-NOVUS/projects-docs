# ПОВНИЙ МОДУЛЬНИЙ МАЙСТЕР-ПЛАН — AGENT CORE (КАНОНІЧНИЙ SSoT)

Статус: ЗАВЕРШЕНО ТА ЗАФІКСОВАНО (Базова версія v0.2.0, 2026-09-25)

Область охоплення: тільки agent-core, з дотриманням міжрепозиторних меж із panel-core та installer.

Нормативні якорі:
- AGENTS.md
- ECOSYSTEM_MANIFEST.md

Цей файл замінює оперативне планування розділення як авторитетний майстер-план.
Робочі артефакти в docs/dev залишаються допоміжними записами, а не паралельним джерелом істини.

## 0. Місія, область охоплення та непорушні обмеження

Місія:
- Розвинути agent-core у модульне середовище виконання Go корпоративного рівня з пріоритетом безпеки, зберігши сумісність із платформою та контракти транспортування.

Непорушні обмеження:
- Жодного дрейфу контрактів gRPC, що порушує сумісність, під час міграції.
- Механізми безпеки залишаються діючими на всьому шляху (TLS, підписані метадані, захист від повторів, обмеження частоти запитів, аудит).
- Жодної втрати бізнес-можливостей для телеметрії, операцій середовища виконання, VFS, резервного копіювання, PTY, консолі WebSocket, SSH/SFTP.
- Детерміновані фазові контрольні точки з відтворюваною валідацією.
- Збереження сумісності Installer та Panel між релізами.

## 1. Авторитетні інваріанти продукту та контрактів

## 1.1 Поверхня API та вирішення розбіжностей контрактів (Contract Drift)

Авторитетне рішення:
- BackupService та ReinstallInstance залишаються офіційною поверхнею gRPC-контракту платформи.

Обов'язковий інваріант:
- Джерело контракту в proto/novus.proto, згенеровані стаби (stubs) та реєстрація у рантаймі розглядаються як неподільна базисна лінія (baseline).

Застосування:
- Тест захисту від розбіжностей контрактів є обов'язковим у CI та локальних шлюзах (gates).
- Будь-яке додавання чи видалення сервісу/методу вимагає узгодженого джерела контракту, згенерованого коду, обробників, тестів, документації та послідовності релізів.

## 1.2 Інваріанти зміцнення транспорту (WebSocket та SSH)

Авторитетне рішення:
- WebSocket та SSH залишаються увімкненими за замовчуванням.

Обов'язкові вимоги щодо зміцнення безпеки:
- WebSocket:
  - Видалити поведінку wild-card (з шаблоном `*`) для CheckOrigin.
  - Застосувати сувору валідацію claims JWT, прив'язану до контексту ноди, контейнера та сесії.
- SSH/SFTP:
  - Ключ хоста має бути постійним і згенерованим лише один раз.
  - Зберігати ключ за безпечним шляхом стану хоста (/etc/novus-agent/ або політика шляху стану, узгоджена з життєвим циклом NOVUS_AGENT_STATE_FILE).
  - Видалити захардкоджений порт :2022 з ініціалізації рантайму та перенести його до конфігурації.
  - Маршрутизувати доступ до диска SFTP через уніфікований VFS Policy Engine.
  - Вимагати канонізації filepath.EvalSymlinks перед усіма реальними операціями з файловою системою.

## 1.3 Архітектурний інваріант VFS: Контекстно-залежний рушій політик OIM/IAM

Архітектура VFS повинна еволюціонувати від вибору бінарної області видимості до детальної обробки політик.

Обов'язкові режими політик:
- режим host_admin:
  - Повний доступ до файлової системи хоста для довірених робочих процесів адміністрування вузлів.
- режим scoped_runtime:
  - Базова ізоляція орендаря/середовища виконання до кореневих каталогів /var/lib/novus/volumes/*.

Обов'язкові можливості детального захисту на рівні шляхів OIM/IAM:
- AllowedSubpaths:
  - Позитивний білий список конкретних піддерев всередині томів середовища виконання.
- HiddenPaths та MaskedPaths:
  - Заборона видимості у списках каталогів та відповідях метаданих для захищених шляхів.
- AccessFlags:
  - Прапорці операцій на рівні шляху: Read, Write, Delete, Chmod.
- Захист від обходу символічних посилань (Symlink-Traverse Guard):
  - Канонізація через filepath.EvalSymlinks із подальшою оцінкою кінцевого цільового об'єкта за масками та прапорцями політик.

Інваріант межі:
- Агент забезпечує виконання технічної області видимості та захисту шляхів; Panel залишається центром прийняття рішень IAM/OIM.

## 1.4 Інваріант конвеєра оновлення бінарних файлів (P0)

Обов'язкова поведінка:
- Повне видалення виконання оновлень на основі скриптів (curl | bash заборонено).
- Конвеєр оновлень має керуватися бінарними файлами:
  - отримання метаданих релізу через GitHub Releases API,
  - завантаження артефакту Linux ELF,
  - перевірка обов'язкової контрольної суми SHA-256,
  - виконання атомарної заміни бінарного файлу за допомогою os.Rename,
  - перезапуск юніта за контрольованою політикою з шляхом відкату у разі невдалих змін.

## 2. Повний звіт про аудит (зведений)

## 2.1 Критичні знахідки

1) Небезпечний шлях виконання оновлювача.
- Докази: internal/grpcserver/service.go (шлях UpdateAgent, що викликає конвеєр командного рядка).
- Ризик: загроза ланцюжку постачання / RCE.

2) Ризик розбіжності історичних контрактів (тепер узгоджено у вихідному контракті та документації, захист збережено).
- Контекст доказів: розбіжність між реєстрацією рантайму та вихідним proto до узгодження.
- Ризик: несумісність панелі/агента та невідтворювана генерація protobuf.

3) Прогалина посилення захисту походження та claims WebSocket.
- Докази: прийняття wildcard походження та недостатня прив'язка контексту.
- Ризик: крос-доменне зловживання / зловживання токенами в транспорті сумісності.

## 2.2 Виявлені проблеми високого рівня (High Findings)

1) Обхід примусового застосування шляхів SFTP порушує єдину політику шляхів у VFS.
- Докази: прямі операції os.* у шляху адаптера SFTP.
- Ризик: несумісна поведінка ізоляції та вразливість до обходу символічних посилань (symlink traversal).

2) Область дії VFS за замовчуванням охоплює корінь всієї хост-системи.
- Докази: параметр bootstrap AllowedRoots встановлено на /.
- Ризик: ізоляція орендарів (tenants) із обмеженою областю дії ще не застосовується за замовчуванням у режимі політики виконання.

3) Борг життєвого циклу та конфігурованості ідентифікатора хоста SSH.
- Докази: неперсистентний життєвий цикл ключа хоста та жорстко закодований порт SSH у шляху ініціалізації (bootstrap).
- Ризик: нестабільність ідентифікації та зниження операційного управління.

## 2.3 Виявлені проблеми середнього рівня (Medium Findings)

1) Неактивні або слабко інтегровані шляхи.
- Інтеграція оркестрації обробника команд (Command handler) та планувальника (scheduler) вимагає чіткого володіння та очищення життєвого циклу.

2) Розбіжність документації (частково усунуто).
- Ключі конфігурації та заяви про поведінку повинні постійно відповідати реальності виконання.

3) Невідповідність щільності покриття для поверхонь високого ризику.
- Транспортні та критичні з погляду безпеки шляхи вимагають глибших цілеспрямованих тестів.

## 4. Стандарт управління документацією (Суворий)

Документація має розвиватися синхронно з архітектурою та реалізацією.

Обов'язкові контури документації:

1) Контур розробника (docs/development/):
- внутрішні компоненти модулів, розширення поверхонь gRPC, контракти типів,
  поведінка протоколу панель-агент, стандарти тестування, контроли придатності.

2) Контур оператора та системного адміністратора (docs/ public operator set):
- конфігурація середовища, відкриті порти, налаштування systemd,
  модель збереження SSH/TLS, стан безпеки, ізоляція мережі, діагностика.

3) Користувацький / довідковий контур (docs/ public reference set):
- довідники змінних середовища, обмеження/можливості VFS,
  функціональні довідники SFTP та веб-консолі.

4) Внутрішній інженерний контур (docs/dev/):
- приватні аудити, реєстри боргу, трекери виконання, нотатки міграції.

Вимога щодо санітарної обробки безпеки:

- Публічна документація має залишатися детально функціональною, але забезпечувати повну заборону на розголошення ланцюжків вразливостей, приватних секретних шляхів хостів, інструкцій з обходу або деталей наступальних операцій.

  - Додано цільові модульні тести для виділених шляхів оркестрації RuntimeSurface.

  - Оркестрацію CreateBackup, RestoreBackup, DeleteBackup та ListBackups перенесено з gRPC транспорту в сервіс додатку модуля.
  - gRPC транспорт BackupService тепер делегує ці шляхи, зберігаючи потокові конверти та мапінг статусів.
  - Додано цільові модульні тести для виділених шляхів BackupOrchestration.

- C4 постачено:

- C5 постачено:

## Фаза D. Реалізація посилення безпеки

- D1 постачено:
  - Шлях оновлення на основі скриптів видалено з `internal/grpcserver/service.go`.
  - Модуль менеджера оновлення бінарних файлів впроваджено в `internal/modules/update_manager/application/service.go`.
  - `UpdateAgent` тепер делегує асинхронний потік оновлення бінарних файлів сервісу додатку модуля.
  - Додано цільові модульні тести для завантаження бінарних файлів менеджером оновлень та потоку їх активації.
- D2 постачено:
  - Впроваджено обов'язкову перевірку SHA-256 для артефактів оновлювача через метадані випуску `checksums.txt`.
  - Активація бінарного файлу тепер відбувається лише після збігу очікуваної контрольної суми із завантаженою.
  - Додано цільові модульні тести для збоїв завантаження контрольної суми, відсутності запису контрольної суми та невідповідності контрольних сум.

## 7. Continuous Evolution: The Anti-Monolithic Modular Invariant
Усі подальші доопрацювання ядра агента підпорядковуються правилу нульової монолітної експансії (Zero-Monolith Policy):   
1) Заборона на розширення загальних і кореневих шарів: Заборонено додавати бізнес-логіку в internal/grpcserver, main.go, загальні хелпери або платформені пакети internal/platform/*.   
2) Маршрутизація функціоналу (Domain Routing):
  - Існуючий домен: Якщо завдання стосується існуючої функціональності (InstanceLifecycle, RuntimeSurface, FilesVFS, UpdateManager тощо), реалізація ведеться виключно всередині відповідного модуля (internal/modules/<Domain>/...).
  - Новий домен: Якщо завдання є новим незалежним контекстом (наприклад, HypervisorKVM, MetricsEngine, TelemetryUDP), воно оформлюється суворо як новий автономний модуль за канонічним стандартом (application, domain, infrastructure, transport).   
3) Слабка зв'язність (Loose Coupling): Міжмодульна взаємодія дозволена лише через публічні інтерфейси портів, шину подій або типізовані контракти без циклічних та інфраструктурних імпортів.
