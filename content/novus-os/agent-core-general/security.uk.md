# NOVUS Agent: Security Model

NOVUS Agent — це хостовий Data-Plane демон. Він приймає лише підтримуваний транспорт Panel і не є універсальною адміністративною кінцевою точкою.

## Trust Boundaries

- gRPC транспорт вимагає TLS.
- Привілейовані запити автентифікуються за допомогою пов'язаної ідентифікації Panel, підписаного запиту, перевірки актуальності, захисту від повторного відтворення (Replay Guard) та обмеження кількості запитів для кожного ідентифікатора.
- Після створення пари Agent прив'язується до однієї Panel. Запит від іншого ідентифікатора Panel відхиляється.
- Об'єднання в пару, видалення прав власності (unclaim) та ротація секретів є чутливими до безпеки операціями Control-Plane і мають ініціюватися через затверджений робочий процес Panel.

Реалізація підписання, політика часу, секретні матеріали та деталі зберігання стану є внутрішньою інформацією безпеки. Використовуйте підтримуваний клієнт Panel або згенеровані інструменти контрактів замість реалізації спеціального (ad-hoc) клієнта.

## Host Execution

Agent виконує дозволені операції з контейнерами, файловою системою, телеметрією та терміналом лише після перевірки транспорту. Термінальні сеанси використовують затверджену політику оболонки та передаються через Panel; браузери не отримують прямого доступу до оболонки хоста.

Операції з файловою системою нормалізують запитувані шляхи та застосовують захист від символічних посилань (symlink hardening). Контекстно-залежні політики VFS середовища виконання залишаються активною областю посилення захисту; оператори не повинні припускати ізоляцію орендарів (tenants) за межами поточного підтримуваного робочого процесу та призначених дозволів Panel.

## Аудит та операції

Коли ведення журналу аудиту ввімкнено, Agent генерує структуровані події життєвого циклу безпеки запитів для операційного огляду. Вважайте записи аудиту конфіденційними: вони можуть містити назви методів, причини та ідентифікатори Panel.

Оператори повинні:

1. Розгортати Agent лише через затверджений шлях випуску та встановлення.
2. Обмежувати мережеву доступність відповідно до затвердженої інфраструктурної політики.
3. Моніторити доступність Agent та збої автентифікації через Panel і систему спостережуваності хоста.
4. Ротувати облікові дані створення пари за допомогою підтримуваного потоку Control-Plane.
5. Зберігати секрети, матеріали TLS, токени створення пари та журнали хоста поза межами систем контролю версій та публічних каналів підтримки.

Щодо підтримуваних налаштувань дивіться [Configuration Reference](CONFIGURATION.md). Внутрішні
результати реалізації обмежені інженерним робочим простором.
