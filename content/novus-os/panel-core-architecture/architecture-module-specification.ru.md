# СПЕЦИФИКАЦИЯ МОДУЛЯ

Статус: нормативный
Владелец: Panel Core Engineering
Область: архитектура модуля panel-core
Последнее обновление: 2026-09-24
Якоря: [AGENTS.md](../../AGENTS.md), [ECOSYSTEM_MANIFEST.md](../../ECOSYSTEM_MANIFEST.md), [Master Plan WS-D](../dev/MASTER_PLAN_PANEL_ENTERPRISE_AAA_2026-09-23.md)

## 1. Назначение и область применения парка (Fleet Scope)

Настоящая спецификация является золотым стандартом для проектирования, аудита и рефакторинга модулей в NOVUS-OS Panel.

NOVUS-OS представляет собой корпоративный многоузловой Control-Plane для:

1. Виртуальной инфраструктуры (VPS и облачные узлы).
2. Физической инфраструктуры (bare-metal серверы).
3. Оркестрации среды выполнения и управления жизненным циклом.
4. Мониторинга сервисов и наблюдаемости за состоянием хостов/сервисов.
5. ServiceDesk и рабочих процессов управления инцидентами.
6. Веб-сайтов (Nginx, PHP-FPM, жизненный цикл SSL).
7. Изоляции баз данных и операций с базами данных клиентов (tenant).
8. Резервного копирования и операций на платформе.

Модель топологии:

1. Panel — это оркестратор уровня Control-Plane (политики, намерения, состояние, контракт API).
2. Agent — это демон уровня execution-plane на управляемых узлах.
3. Installer выполняет только первичную настройку (bootstrap) и не отвечает за оркестрацию времени выполнения.

Поддерживаемые профили развертывания:

1. Парк bare-metal серверов.
2. Парк VPS/KVM.
3. Парк облачных виртуальных машин.
4. Гибридный парк (смешанные классы узлов под управлением одного control-plane).

## 2. Архитектурные инварианты (Строгое соответствие)

Эти правила являются обязательными для всех новых модулей и всех рефакторингов.

1. Запрещено использование слоя фасадов фреймворка для реализации поведения во время выполнения модуля.
2. Регистрация и разрешение сервисов выполняются через [app/Support/Container.php](../../app/Support/Container.php).
3. Композиция маршрутов выполняется через пользовательские контракты роутера в [app/Http/Router.php](../../app/Http/Router.php) и [routes/api.php](../../routes/api.php).
4. Персистентность Control-Plane использует PostgreSQL 18 через нативные соединения PDO `os`, `id` и `sd`.
5. Операции с БД тенантов Data-Plane используют MariaDB 11.4+ через соединение PDO `payload`.
6. Прямое выполнение команд хоста из контроллеров/сервисов панели запрещено (`shell_exec`, `exec`, `proc_open`, `passthru`, `system`).
7. Операции на хосте и в среде выполнения разрешены только через типизированные контрактные транспорты Agent с использованием [app/Services/Agent/NovusAgentClient.php](../../app/Services/Agent/NovusAgentClient.php).
8. Стилизация модулей Vue должна использовать токенизированные семантические классы Tailwind и переменные тем из [config/themes.php](../../config/themes.php).
9. Использование `<style scoped>` и встроенных стилей `style="..."` в шаблонах Vue для интерфейсов модулей запрещено.
10. Строковые литералы i18n в шаблонах Vue запрещены; текст модуля должен поступать из словарей `resources/locales/{ru,en,uk}`.

## 3. Проект бэкенд-домена (app/Modules/<Domain>/)

### 3.1 Обязательная структура каталогов

Каждый модуль бэкенд-домена должен содержать следующие каталоги и разделение ролей:

1. `Http/` для обработчиков конечных точек / контроллеров, регистрируемых в контейнере.
2. `Services/` для бизнес-логики домена и оркестрации.
3. `Providers/` для файлов детерминированной регистрации в контейнере.
4. `Routes/` для манифестов маршрутов домена.

Минимальный скелет:

```text
app/Modules/<Domain>/
├── Http/
│   └── controllers.php
├── Services/
│   └── runtime_services.php
├── Providers/
│   ├── <domain>_core.php
│   └── <domain>_http.php
└── Routes/
    └── api.php
```

### 3.2 Требования к слою Http

1. API-контроллеры должны наследоваться от `App\Controllers\Api\ApiController`.
2. Успешные ответы должны использовать детерминированные контракты-обертки (хэлпер контроллера `ok` и/или `Response::json` с `{ ok: true, data: ... }`).
3. Ответы с ошибками должны использовать детерминированные контракты-обертки через хэлпер сбоя контроллера (каноническая форма: `{ ok: false, error: { code, message } }` с полями совместимости, если это требуется текущей политикой миграции).
4. Произвольные строковые полезные данные `error` запрещены для эндпоинтов, не относящихся к протокольным.
5. Обработчики маршрутов должны быть «тонкими» адаптерами: нормализация входных данных, шлюз разрешений, вызов сервиса, детерминированное маппирование ответа.

### 3.3 Политика исключений протоколов (OAuth 2.0 / OIDC)

Правило детерминированного конверта имеет явное протокольное исключение:

1. Эндпоинты протоколов OAuth 2.0 / OIDC (например, [app/Controllers/Api/OidcProtocolController.php](../../app/Controllers/Api/OidcProtocolController.php)) должны следовать формату ошибок, совместимому с RFC 6749.
2. Допустимый формат полезной нагрузки ошибки протокола:

```json
{
  "error": "invalid_request",
  "error_description": "Missing parameter: client_id"
}
```

3. Эндпоинты протоколов, подпадающие под это исключение, должны покрываться специализированными тестами протоколов, подтверждающими поведение, совместимое с RFC.
4. Это исключение является узкоспециализированным и не должно повторно использоваться API не-протокольных панелей.

### 3.4 Требования к уровню сервисов

1. Сервисы содержат бизнес-логику, переходы состояний и границы транзакций.
2. Сервисы не должны генерировать сырые объекты HTTP-ответов.
3. Сервисы не должны вызывать команды хоста напрямую.
4. Мутации среды выполнения и хоста должны делегироваться типизированным методам `NovusAgentClient`.
5. Типы ввода/вывода должны быть детерминированными и поддаваться аудиту.

### 3.5 Провайдеры и связывание при инициализации (bootstrap wiring)

1. Регистрации в контейнере модулей должны быть детерминированными и базироваться на файлах.
2. Регистрации должны быть совместимы с [app/Support/Container.php](../../app/Support/Container.php).
3. Файлы провайдеров модулей должны загружаться в соответствии со скоординированным порядком инициализации (см. [app/Modules/SystemCore/Providers/bootstrap_orchestrator.php](../../app/Modules/SystemCore/Providers/bootstrap_orchestrator.php)).
4. Порядок регистрации провайдеров должен быть только с добавлением новых элементов (append-only), если явный план миграции не предполагает иное.

### 3.6 Маршруты и применение ограничений доступа

1. Каждый модуль должен содержать изолированный по домену манифест маршрутов в `Routes/api.php`.
2. Манифесты маршрутов модулей должны подключаться через [routes/api.php](../../routes/api.php), а не внедряться произвольным образом в несвязанные модули.
3. Политика разрешений должна применяться для каждого изменяемого endpoint.
4. Обязательный контракт именования разрешений: `platform.<domain>.<action>`.
5. Применение разрешений должно осуществляться посредством контракта middleware разрешений и/или вспомогательных средств защиты ApiController (guard helpers) с детерминированным поведением отказа в доступе.

## 4. Архитектурный план фронтенд-домена (resources/js/modules/<Domain>/)

### 4.1 Требуемая структура каталогов

```text
resources/js/modules/<Domain>/
├── views/
├── components/
├── api/
├── stores/
└── locales/
```

Если унаследованный (legacy) домен еще не содержит все каталоги, в бэклоге миграции должно отслеживаться приведение к данной структуре.

### 4.2 Стандарты Vue SFC и UI

1. Режимом написания по умолчанию является Vue 3 SFC с использованием script setup.
2. Использование `<style scoped>` запрещено.
3. Использование инлайн-атрибутов стилей для поверхностей модулей запрещено.
4. Обязательным требованием является использование токенизированных классов Tailwind и общих переменных темы.
5. Для поведения модальных окон и окон интерфейса используйте общие компоненты работы с окнами и оболочкой (например, [resources/js/modules/Common/components/DesktopWindowWrapper.vue](../../resources/js/modules/Common/components/DesktopWindowWrapper.vue)).
6. Жестко закодированные видимые пользователем строки в шаблонах запрещены.

### 4.3 Типизация фронтенд-транспорта

1. Каждый адаптер API модуля (`api/<domain>Api.ts`) должен использовать унифицированный типизированный транспорт (целевой `novusFetch<T>` определяется WS-D.2).
2. Типизация ответов API должна моделировать детерминированные контракты сервера.
3. Обработка ошибок аутентификации и сессий должна быть централизованной и не создавать циклов.
4. Использование транспортных оберток на уровне модуля, которые обходят унифицированное маппирование ошибок, запрещено.

## 5. Правила доступа Data-Plane и Control-Plane

### 5.1 Использование базы данных Control-plane

Используйте соединения PostgreSQL control-plane (`os`, `id`, `sd`) для состояния панели и состояния identity/service-desk.

Пример (control-plane):

```php
$os = $this->connections->connection('os');
$id = $this->connections->connection('id');
$sd = $this->connections->connection('sd');
```

### 5.2 Использование базы данных Data-plane

Используйте соединение MariaDB с полезной нагрузкой (payload) только для баз данных тенантов/пользователей:

```php
$payload = $this->connections->connection('payload');
```

Эта граница является обязательной, и ее нельзя обходить путем прямого конструирования DSN в логике модуля.

### 5.3 Типизированные помощники запросов и identity

1. Используйте [app/Services/Database/DatabaseHelper.php](../../app/Services/Database/DatabaseHelper.php) для нормализации параметров и безопасного маппинга JSON/JSONB.
2. Используйте идентификаторы UUIDv7 через [app/Support/UuidV7.php](../../app/Support/UuidV7.php) для корреляции сущностей и запросов там, где контракты модулей требуют сгенерированных идентификаторов.
3. Логика модуля должна разделять SQL-запросы control-plane и data-plane с помощью явного указания назначения соединения.

## 6. Оркестрация хостов и правила транспорта

### 6.1 Разрешенный путь выполнения операций на хосте

1. Панель получает намерение через аутентифицированный эндпоинт API.
2. Панель проверяет разрешения IAM/OIM.
3. Панель сопоставляет намерение с типизированным Agent RPC через `NovusAgentClient`.
4. Агент выполняет локальную для хоста операцию и возвращает типизированный результат.
5. Панель сопоставляет результат с детерминированным контрактом ответа API.

### 6.2 Запрещенные паттерны в модулях панели

Внутри контроллеров/сервисов панели запрещено следующее:

1. `shell_exec`, `exec`, `proc_open`, `passthru`, `system`.
2. Прямой доступ к `docker.sock`.
3. Владение локальным PTY в рантайме панели.
4. Оркестрация команд с правами root из HTTP-путей панели.

Технический долг, обнаруженный в уставших интерфейсах, не является прецедентом для нового кода.

## 7. Обеспечение соблюдения контрактов и шлюзы качества

### 7.1 Шлюзы валидации

Обеспечение качества WS-D основано на существующих и планируемых проверках:

1. Проверки целостности ссылок в документации.
2. Проверки быстрого пайплайна качества.
3. Скрипт контроля контрактов модулей: [tools/quality/module_contract_check.php](../../tools/quality/module_contract_check.php).

### 7.2 Критерии провала CI

Изменение модуля должно приводить к провалу CI при выполнении любого из условий:

1. Непротокольный API endpoint возвращает недетерминированную структуру ошибки.
2. В контроллерах/сервисах модуля обнаружен запрещенный паттерн host-exec.
3. Vue-шаблоны модуля содержат `<style scoped>` или атрибуты инлайн-стилей.
4. Vue-шаблоны модуля включают захардкоженные пользовательские литералы вместо ключей i18n.
5. Изменения поверхности маршрутов не согласованы с манифестами доменных маршрутов и политикой прав доступа.

### 7.3 Обязательные проверки для WS-D.1 и более поздних версий

Запускайте и поддерживайте в успешном состоянии:

1. `php tools/quality/docs_link_check.php`
2. `npm run quality:fast`

## 8. Эталонные образцы и базовый уровень аудита

### 8.1 Эталонный образец бэкенда

Эталонный модуль: [app/Modules/Databases](../../app/Modules/Databases)

Ожидания от аудита:

1. Явные границы подключений.
2. Регистрация на основе контейнера.
3. Владение манифестом доменных маршрутов.
4. Детерминированное маппинг-контрактов API.

### 8.2 Эталонный образец фронтенда

Эталонный модуль: [resources/js/modules/Services](../../resources/js/modules/Services)

Требования аудита:

1. Изоляция компонентов по доменам.
2. Использование токенов Tailwind и соответствие теме.
3. Интеграция с общей оболочкой/окном.
4. Постепенная сходимость к полному контракту макета модуля.

## 9. Процедура внедрения

1. Создание нового модуля должно начинаться с этой спецификации.
2. Планы рефакторинга существующих модулей должны ссылаться на эту спецификацию в рамках задачи.
3. Любое исключение требует явной записи архитектурного решения (architecture decision record) в `docs/dev` с указанием владельца и срока действия.
4. В случае конфликта между этим документом и любым более старым руководством, данный документ является приоритетным для архитектуры модулей.
