# СПЕЦИФИКАЦИЯ МОДУЛЯ

Статус: нормативный
Владелец: Panel Core Engineering
Область применения: архитектура модуля panel-core
Последнее обновление: 2026-09-24
Якоря: [AGENTS.md](../../AGENTS.md), [ECOSYSTEM_MANIFEST.md](../../ECOSYSTEM_MANIFEST.md), [Master Plan WS-D](../dev/MASTER_PLAN_PANEL_ENTERPRISE_AAA_2026-09-23.md)

## 1. Назначение и область применения для парка узлов

Настоящая спецификация является золотым стандартом для проектирования, аудита и рефакторинга модулей в NOVUS-OS Panel.

NOVUS-OS представляет собой корпоративный многоузловой Control-Plane для:

1. Виртуальной инфраструктуры (VPS и облачные узлы).
2. Физической инфраструктуры (bare-metal серверы).
3. Оркестрации среды выполнения и управления жизненным циклом.
4. Мониторинга сервисов и наблюдаемости состояния здоровья хостов/сервисов.
5. Рабочих процессов ServiceDesk и управления инцидентами.
6. Веб-сайтов (Nginx, PHP-FPM, жизненный цикл SSL).
7. Изоляции баз данных и операций с базами данных клиентов.
8. Резервного копирования и операций на платформе.

Модель топологии:

1. Panel — это оркестратор Control-Plane (политики, намерения, состояние, контракт API).
2. Agent — это демон Data-Plane на управляемых узлах.
3. Installer выполняет только начальную загрузку и не отвечает за оркестрацию времени выполнения.

Поддерживаемые профили развертывания:

1. Парк bare-metal серверов.
2. Парк VPS/KVM.
3. Парк облачных ВМ.
4. Гибридный парк (смешанные классы узлов под управлением единого control plane).

## 2. Архитектурные инварианты (Строгое соответствие)

Эти правила являются обязательными для всех новых модулей и всех рефакторингов.

1. Запрещено использовать слой фасадов фреймворка для реализации поведения во время выполнения модуля.
2. Регистрация и разрешение сервисов выполняются через [app/Support/Container.php](../../app/Support/Container.php).
3. Композиция маршрутов выполняется через пользовательские контракты роутера в [app/Http/Router.php](../../app/Http/Router.php) и [routes/api.php](../../routes/api.php).
4. Персистентность Control-Plane использует PostgreSQL 18 через нативные PDO-соединения `os`, `id` и `sd`.
5. Операции с БД тенантов Data-Plane используют MariaDB 11.4+ через PDO-соединение `payload`.
6. Прямое выполнение команд на хосте из контроллеров/сервисов панели запрещено (`shell_exec`, `exec`, `proc_open`, `passthru`, `system`).
7. Операции на хосте и в рантайме разрешены только через типизированные контрактные транспорты Agent с использованием [app/Services/Agent/NovusAgentClient.php](../../app/Services/Agent/NovusAgentClient.php).
8. Стилизация Vue-модулей должна использовать токенизированные семантические классы Tailwind и переменные темы из [config/themes.php](../../config/themes.php).
9. Использование `<style scoped>` и инлайновых стилей `style="..."` во Vue-шаблонах запрещено для интерфейсов модулей.
10. Использование литералов i18n во Vue-шаблонах запрещено; текст модуля должен поступать из словарей `resources/locales/{ru,en,uk}`.

## 3. Проект бэкенд-домена (app/Modules/<Domain>/)

### 3.1 Обязательная структура каталогов

Каждый модуль бэкенд-домена должен содержать следующие каталоги и разделение ролей:

1. `Http/` для обработчиков эндпоинтов/контроллеров, регистрируемых в контейнере.
2. `Services/` для бизнес-логики домена и оркестрации.
3. `Providers/` для детерминированных файлов регистрации в контейнере.
4. `Routes/` для манифестов маршрутов домена.

Минимальный скелет:

```text
app/Modules/<Domain>/
├── Http/
│   └── controllers.php
├── Services/
│   └── runtime_services.php
├── Providers/
│   ├── <domain>_core.php
│   └── <domain>_http.php
└── Routes/
    └── api.php
```

### 3.2 Требования к уровню Http

1. API-контроллеры должны наследоваться от `App\Controllers\Api\ApiController`.
2. Успешные ответы должны использовать детерминированные контракты-обертки (хэлпер контроллера `ok` и/или `Response::json` с `{ ok: true, data: ... }`).
3. Ответы об ошибках должны использовать детерминированные контракты-обертки через хэлперы сбоя контроллера (каноническая форма: `{ ok: false, error: { code, message } }` с полями совместимости, если это требуется текущей политикой миграции).
4. Произвольные строковые пейлоады `error` запрещены для непротокольных эндпоинтов.
5. Обработчики маршрутов должны быть «тонкими» адаптерами: нормализация входных данных, проверка прав доступа, вызов сервиса, детерминированное маппирование ответа.

### 3.3 Політика протокол-ісключень (OAuth 2.0 / OIDC)

Правило детермінистичного конверта має явний виняток для протоколів:

1. Ендпоінти протоколів OAuth 2.0 / OIDC (наприклад, [app/Controllers/Api/OidcProtocolController.php](../../app/Controllers/Api/OidcProtocolController.php)) повинні відповідати формату помилок, сумісному з RFC 6749.
2. Дозволений формат корисного навантаження помилки протоколу:

```json
{
  "error": "invalid_request",
  "error_description": "Missing parameter: client_id"
}
```

3. Ендпоінти протоколів, на які поширюється цей виняток, повинні бути покриті спеціалізованими протокольними тестами, що доводять сумісну з RFC поведінку.
4. Цей виняток є вузькоспеціалізованим і не повинен використовуватися повторно API не-протольних панелей.

### 3.4 Вимоги до рівня сервісів

1. Сервіси містять бізнес-логіку, переходи станів та межі транзакцій.
2. Сервіси не повинні створювати «сирі» об'єкти HTTP-виводу.
3. Сервіси не повинні викликати команди хоста безпосередньо.
4. Зміни середовища виконання та хоста мають делегуватися типізованим методам `NovusAgentClient`.
5. Типи вводу/виводу повинні бути детермінованими та придатними для аудитів.

### 3.5 Провайдеры и инициализация (bootstrap)

1. Регистрации контейнеров модулей должны быть детерминированными и файловыми.
2. Регистрации должны быть совместимы с [app/Support/Container.php](../../app/Support/Container.php).
3. Файлы провайдеров модулей должны загружаться в соответствии с упорядоченной последовательностью инициализации (см. [app/Modules/SystemCore/Providers/bootstrap_orchestrator.php](../../app/Modules/SystemCore/Providers/bootstrap_orchestrator.php)).
4. Порядок регистрации провайдеров должен быть только с добавлением в конец (append-only), если иное явно не предусмотрено планом миграции.

### 3.6 Маршруты и контроль разрешений

1. Каждый модуль должен содержать изолированный по домену манифест маршрутов в `Routes/api.php`.
2. Манифесты маршрутов модулей должны подключаться через [routes/api.php](../../routes/api.php), а не встраиваться бессистемно в несвязанные модули.
3. Политика разрешений должна применяться для каждого изменяющего состояние эндпоинта.
4. Обязательный контракт именования разрешений: `platform.<domain>.<action>`.
5. Контроль разрешений должен осуществляться с помощью контракта middleware разрешений и/или вспомогательных средств защиты ApiController, с детерминированным поведением отказа в доступе.

## 4. Архитектурный план фронтенд-домена (resources/js/modules/<Domain>/)

### 4.1 Требуемая структура каталогов

```text
resources/js/modules/<Domain>/
├── views/
├── components/
├── api/
├── stores/
└── locales/
```

Если унаследованный домен еще не содержит все каталоги, в бэклоге миграции должна отслеживаться конвергенция к этой структуре.

### 4.2 Стандарты Vue SFC и UI

1. Vue 3 SFC с режимом script setup является стандартным способом написания кода.
2. Использование `<style scoped>` запрещено.
3. Атрибуты стилей в строках (inline style) запрещены для поверхностей модулей.
4. Использование токенизированных классов Tailwind и общих переменных темы является обязательным.
5. Повторно используйте общие компоненты работы с окнами и оболочкой для реализации поведения модальных окон / окон (например, [resources/js/modules/Common/components/DesktopWindowWrapper.vue](../../resources/js/modules/Common/components/DesktopWindowWrapper.vue)).
6. Жестко закодированные видимые пользователем строки в шаблонах запрещены.

### 4.3 Типизация фронтенд-транспорта

1. Каждый адаптер API модуля (`api/<domain>Api.ts`) должен использовать унифицированный типизированный транспорт (`novusFetch<T>`, цель которого определена в WS-D.2).
2. Типизация ответов API должна моделировать детерминированные контракты сервера.
3. Обработка ошибок аутентификации/сессии должна быть централизованной и исключающей зацикливание.
4. Транспортные обертки на уровне модулей, которые обходят унифицированное сопоставление ошибок, запрещены.

## 5. Правила доступа Data-Plane и Control-Plane

### 5.1 Использование базы данных control-plane

Используйте соединения PostgreSQL для control-plane (`os`, `id`, `sd`) для состояния панели, а также состояния identity и service-desk.

Пример (control-plane):

```php
$os = $this->connections->connection('os');
$id = $this->connections->connection('id');
$sd = $this->connections->connection('sd');
```

### 5.2 Использование базы данных data-plane

Используйте соединение MariaDB с полезной нагрузкой (payload) только для баз данных тенантов/пользователей:

```php
$payload = $this->connections->connection('payload');
```

Эта граница является обязательной и не должна обходиться путем прямой сборки DSN в логике модуля.

### 5.3 Типизированные хелперы запросов и identity

1. Используйте [app/Services/Database/DatabaseHelper.php](../../app/Services/Database/DatabaseHelper.php) для нормализации параметров и безопасного маппинга JSON/JSONB.
2. Используйте идентификаторы UUIDv7 через [app/Support/UuidV7.php](../../app/Support/UuidV7.php) для корреляции сущностей/запросов там, где контракты модулей требуют сгенерированных идентификаторов.
3. Логика модуля должна разделять SQL-задачи control-plane и data-plane посредством явного указания намерения соединения.

## 6. Оркестрация хостов и правила транспорта

### 6.1 Разрешенный путь выполнения операций на хосте

1. Панель получает намерение через аутентифицированный API-эндпоинт.
2. Панель валидирует разрешения IAM/OIM.
3. Панель сопоставляет намерение с типизированным Agent RPC через `NovusAgentClient`.
4. Агент выполняет локальную для хоста операцию и возвращает типизированный результат.
5. Панель сопоставляет результат с детерминированным контрактом API-ответа.

### 6.2 Запрещенные паттерны в модулях панели

Внутри контроллеров/сервисов панели запрещено следующее:

1. `shell_exec`, `exec`, `proc_open`, `passthru`, `system`.
2. Прямой доступ к `docker.sock`.
3. Владение локальным PTY в рантайме панели.
4. Оркестрация команд с правами root из HTTP-путей панели.

Технический долг, обнаруженный в устаревших компонентах, не является прецедентом для нового кода.

## 7. Обеспечение соблюдения контрактов и шлюзы качества

### 7.1 Шлюзы валидации

Контроль качества WS-D основан на существующих и планируемых проверках:

1. Проверки целостности ссылок в документации.
2. Проверки быстрого конвейера качества.
3. Скрипт контроля контрактов модулей: [tools/quality/module_contract_check.php](../../tools/quality/module_contract_check.php).

### 7.2 Критерии падения CI

Изменение модуля должно приводить к падению CI при выполнении любого из следующих условий:

1. Непротокольный API endpoint возвращает не детерминированную структуру ошибки.
2. В контроллерах/сервисах модуля обнаружен запрещенный паттерн host-exec.
3. Vue-шаблоны модуля содержат `<style scoped>` или встроенные атрибуты стилей (inline style).
4. Vue-шаблоны модуля включают захардкоженные пользовательские литералы вместо ключей i18n.
5. Изменения поверхности маршрутов не согласованы с манифестами доменных маршрутов и политикой прав доступа.

### 7.3 Обязательные проверки для WS-D.1 и более поздних версий

Запускайте и поддерживайте в зеленом состоянии:

1. `php tools/quality/docs_link_check.php`
2. `npm run quality:fast`

## 8. Эталонные реализации и базовый уровень аудита

### 8.1 Эталонная реализация бэкенда

Эталонный модуль: [app/Modules/Databases](../../app/Modules/Databases)

Ожидания от аудита:

1. Явные границы подключений.
2. Регистрация на основе контейнеров.
3. Владение манифестом доменных маршрутов.
4. Детерминированное маппирование контракта API.

### 8.2 Эталонный образец фронтенда

Эталонный модуль: [resources/js/modules/Services](../../resources/js/modules/Services)

Требования аудита:

1. Изоляция компонентов по доменам.
2. Использование токенов Tailwind и соответствие теме.
3. Интеграция с общей оболочкой/окном.
4. Постепенная сходимость к полному контракту макета модуля.

## 9. Процедура внедрения

1. Создание нового модуля должно начинаться с этой спецификации.
2. Планы рефакторинга существующих модулей должны ссылаться на эту спецификацию в области задач.
3. Любое исключение требует явной записи архитектурного решения (Architecture Decision Record) в каталоге `docs/dev` с указанием ответственного и срока действия.
4. В случае конфликта между настоящим документом и любыми более ранними руководствами, приоритет в вопросах архитектуры модулей имеет настоящий документ.
