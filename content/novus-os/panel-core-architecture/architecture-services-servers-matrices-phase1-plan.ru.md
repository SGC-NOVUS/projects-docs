# План реорганизации служб, серверов и матриц NOVUS OS — Фаза 1

## Директива (согласно запросу)

Выступите в роли Главного корпоративного архитектора и Ведущего инженера по UI/UX. Подтвердите получение этой директивы, ознакомьтесь с эталонными спецификациями panel-main и предоставьте пошаговый технический план для Фазы 1. Приступите к реализации сразу после предоставления плана.

## Подтверждение

Директива принята. Данный план Фазы 1 базируется на:
- доменном поведении panel-main (жизнеспособность нод, выбор аллокаций, управление переменными и оркестрация создания серверов)
- текущей топологии рантайма panel-novus (инстанс-центричная модель, пул сетевых каналов, таблицы профилей)
- текущих лимитах конверта agent-core (только частичные cgroups для CPU/RAM)

## Архитектурный разворот (2026-05-22)

Разворот до Фазы 1 принят и применен:
1. Реестр нод переведен с приоритета файловой системы на приоритет базы данных в `panel_nodes`.
2. Каноническое хранилище аллокаций перенесено в `panel_node_allocations`, связанное с `panel_nodes.id`.
3. Устаревшие файлы состояния JSON остаются в качестве резервного источника совместимости / источника импорта на время перехода.

## Непреложные ограничения

1. Запрещен прямой копипаст кода из panel-main.
2. Сохраняйте публичные API, используемые текущим фронтендом panel-novus и агентами.
3. Внедрите каноническую схему и сервисы с путями обратной совместимости (fallback).
4. Обеспечьте строгую проверку ресурсов там, где емкость настроена явно.

## Реконструированная логика panel-main (математическая/архитектурная)

1. Формула жизнеспособности ноды:
- effective_limit = base_capacity * (1 + overallocate_pct / 100)
- viable(resource) = (current_committed + requested) <= effective_limit

2. Политика выбора аллокации:
- поиск свободных кандидатов IP:port на целевой ноде
- выделенный (dedicated) режим исключает адреса, уже занятые другими привязками
- детерминированный выбор первого доступного может заменить случайный выбор для обеспечения воспроизводимости

3. Схема конвейера провижининга:
- определение жизнеспособной ноды
- определение аллокации(ий)
- валидация переменных/правил
- сохранение сервера/инстанции
- отправка команды на создание рантайма

4. Управление переменными:
- зарезервированные ключи окружения блокируются
- динамические правила валидации применяются перед коммитом

## Phase 1 Scope (This Wave)

1. Каноническая модель пула нод в novus_os.
2. Каноническая таблица выделений (allocations) и сервис аллокатора.
3. Проверки ресурсного журнала в режиме жесткого отказа (hard-deny) на путях создания/записи ресурсов.
4. Строгая передача конверта лимитов рантайма в полезную нагрузку создания контейнера.
5. Расширение Proto в agent-core (аддитивное, с обратной совместимостью).

## Step-by-Step Technical Plan

1. Основа схемы данных:
- добавить идемпотентную миграцию для создания/патча `panel_nodes`
- добавить идемпотентную миграцию для создания/патча `allocations`
- заполнить `panel_nodes` на основе наблюдаемых `node_agent_id` в таблицах рантайма
- заполнить `allocations` из `panel_network_channels` для непрерывности перехода

2. Доменные сервисы:
- добавить `NodeResourceLedgerService` для вычисления использованных/свободных лимитов с учетом оверселлинга
- добавить `AllocationPoolService` для резервирования первого доступного IP:port из `allocations`

3. Настройка конвейера:
- принудительно применять проверки журнала в `InstanceMutationService::create()`
- принудительно применять проверки журнала в `InstanceProfileService::saveResources()` с самоисключением
- обновить `ProvisioningService` для использования пула `allocations` в приоритетном порядке с запасным вариантом (fallback) на устаревшие `panel_network_channels`, если канонический пул не активен

4. Транспорт строгих лимитов:
- расширить полезную нагрузку провижининга полями disk/swap/oom/pids
- расширить маппинг запроса создания docker и конфигурации хоста в agent-core для принудительного применения cgroups/storage/pids там, где это поддерживается

5. Расширение контракта:
- добавить аддитивное сообщение `ContainerHardwareLimits` в `agent-core/proto/novus.proto`
- прикрепить необязательный конверт лимитов в `DockerManagerRequest` (без ломающих изменений RPC)
- регенерировать `internal/gen/novus/v1/*.pb.go`

6. Верификация:
- обновление целевых юнит-тестов panel-novus (построитель полезной нагрузки)
- проверки синтаксиса и линтера в измененных PHP-файлах
- `go test ./...` и `go build ./...` в agent-core

7. План развертывания:

- сохранить распределитель устаревших сетевых каналов в качестве запасного варианта
- включить канонические выделения на основе наличия данных, а не по принципу единовременного перехода (flag day)

## Deliverables of Phase 1

1. Артефакты канонической схемы (`panel_nodes`, `allocations`) с идемпотентной миграцией.
2. Принудительное жесткое отклонение в реестре ресурсов.
3. Сервис распределения по принципу «первый доступный» и интеграция подготовки ресурсов.
4. Конверт строгих ограничений среды выполнения, передаваемый сквозным образом (end-to-end).
5. Аддитивное обновление proto-контракта и пересозданные заглушки.
