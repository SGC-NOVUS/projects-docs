# Регламент модернизации служб/серверов/матриц NOVUS-OS — План Фазы 1

## Директива (согласно запросу)

Выступите в роли главного корпоративного архитектора (Principal Enterprise Architect) и ведущего инженера по UI/UX. Подтвердите получение этой директивы, ознакомьтесь с эталонной реализацией panel-main и предоставьте пошаговый технический план для Фазы 1. Приступить к реализации немедленно после утверждения плана.

## Подтверждение

Директива принята. Данный план Фазы 1 основывается на:
- доменном поведении panel-main (жизнеспособность нод, выбор аллокаций, управление переменными и оркестрация создания серверов);
- текущей топологии рантайма panel-novus (инстанс-центричная модель, пул сетевых каналов, таблицы профилей);
- текущих лимитах конверта agent-core (только частичные cgroups для CPU/RAM).

## Архитектурный поворот (2026-05-22)

Поворот перед Фазой 1 принят и применен:
1. Реестр нод переведен с приоритета файловой системы на приоритет базы данных в `panel_nodes`.
2. Каноническое хранилище аллокаций перенесено в `panel_node_allocations`, связанное с `panel_nodes.id`.
3. Устаревшие файлы состояния JSON остаются в качестве резервного варианта совместимости / источника импорта на время переходного периода.

## Non-Negotiable Constraints

1. Запрещен прямой копипаст кода из panel-main.
2. Сохранять публичные API, используемые текущим фронтендом panel-novus и агентами.
3. Внедрить каноническую схему и сервисы с путями обратной совместимости (fallback paths).
4. Принудительно применять строгие проверки ресурсов там, где емкость настроена явно.

## panel-main Logic Reconstructed (Mathematical/Architectural)

1. Формула жизнеспособности ноды (Node viability formula):
- effective_limit = base_capacity * (1 + overallocate_pct / 100)
- viable(resource) = (current_committed + requested) <= effective_limit

2. Политика выбора размещения (Allocation selection policy):
- найти свободные кандидаты IP:port на целевой ноде
- выделенный режим (dedicated mode) исключает адреса, уже занятые другими привязками
- детерминированный выбор первого доступного может заменить случайный выбор для воспроизводимости

3. Структура пайплайна провижининга (Provisioning pipeline shape):
- определить жизнеспособную ноду
- определить размещение (allocation/allocations)
- провалидировать переменные/правила
- персистить сервер/инстанс
- отправить запрос на создание рантайма

4. Управление переменными (Variable governance):
- зарезервированные ключи окружения блокируются
- динамические правила валидации применяются до фиксации (commit)

## Phase 1 Scope (This Wave)

1. Каноническая модель пула нод в novus_os.
2. Каноническая таблица аллокаций и сервис аллокатора.
3. Проверки ресурсного реестра с жестким отказом (hard-deny) на путях создания/записи ресурсов.
4. Пропагация строгого конверта лимитов времени выполнения в полезную нагрузку создания контейнера.
5. Расширение Proto в agent-core (аддитивное, с обратной совместимостью).

## Step-by-Step Technical Plan

1. Основа схемы:
- добавить идемпотентную миграцию для создания/патча `panel_nodes`
- добавить идемпотентную миграцию для создания/патча `allocations`
- заполнить `panel_nodes` на основе наблюдаемого `node_agent_id` в таблицах времени выполнения
- заполнить `allocations` из `panel_network_channels` для непрерывности перехода

2. Доменные сервисы:
- добавить `NodeResourceLedgerService` для вычисления использованных/свободных/лимитных ресурсов с учетом овераллокации
- добавить `AllocationPoolService` для резервирования первого доступного IP:port из `allocations`

3. Настройка пайплайна:
- принудительно применять проверки реестра в `InstanceMutationService::create()`
- принудительно применять проверки реестра в `InstanceProfileService::saveResources()` с исключением самого себя
- обновить `ProvisioningService`, чтобы использовать пул `allocations` в качестве приоритетного и выполнять фоллбек на устаревшие `panel_network_channels`, если канонический пул не активен

4. Транспорт строгих лимитов:
- расширить полезную нагрузку провижининга полями disk/swap/oom/pids
- расширить маппинг запроса создания docker и конфигурации хоста в agent-core для применения cgroups/storage/pids там, где это поддерживается

5. Расширение контракта:
- добавить аддитивное сообщение `ContainerHardwareLimits` в `agent-core/proto/novus.proto`
- прикрепить необязательный конверт лимитов в `DockerManagerRequest` (без ломающих изменений RPC)
- перегенерировать `internal/gen/novus/v1/*.pb.go`

6. Верификация:
- обновление целевых юнит-тестов panel-novus (построитель полезной нагрузки)
- проверки синтаксиса/линтера в измененных PHP-файлах
- `go test ./...` и `go build ./...` в agent-core

7. План развертывания:

- оставить аллокатор устаревших сетевых каналов в качестве запасного пути
- включить канонические аллокации по наличию данных, а не по переходу в день X (flag day cutover)

## Deliverables of Phase 1

1. Артефакты канонической схемы (`panel_nodes`, `allocations`) с идемпотентной миграцией.
2. Принудительное жесткое отклонение (hard-deny) в реестре ресурсов.
3. Сервис аллокатора первого доступного ресурса и интеграция подготовки (provisioning).
4. Строгий конверт ограничений среды выполнения (runtime limits), передаваемый сквозным образом (end-to-end).
5. Аддитивное обновление proto-контракта и перегенерация заглушек.
