# СПЕЦИФІКАЦІЯ МОДУЛЯ

Статус: нормативний
Власник: Panel Core Engineering
Область: архітектура модуля panel-core
Останнє оновлення: 2026-09-24
Якорі: [AGENTS.md](../../AGENTS.md), [ECOSYSTEM_MANIFEST.md](../../ECOSYSTEM_MANIFEST.md), [Master Plan WS-D](../dev/MASTER_PLAN_PANEL_ENTERPRISE_AAA_2026-09-23.md)

## 1. Призначення та область флоту

Ця специфікація є золотим стандартом для проектування, аудитів та рефакторингу модулів у NOVUS OS Panel.

NOVUS OS — це корпоративний багатонодовий control-plane для:

1. Віртуальної інфраструктури (VPS та хмарні ноди).
2. Фізичної інфраструктури (виділені сервери / bare-metal).
3. Оркестрації середовищ виконання та управління життєвим циклом.
4. Моніторингу сервісів та спостережуваності за станом хостів/сервісів.
5. ServiceDesk та робочих процесів управління інцидентами.
6. Вебсайтів (Nginx, PHP-FPM, життєвий цикл SSL).
7. Ізоляції баз даних та операцій з базами даних тенантів.
8. Резервного копіювання та операцій на платформі.

Топологічна модель:

1. Panel є control-plane оркестратором (політика, намір, стан, контракт API).
2. Agent є демоном execution-plane на керованих нодах.
3. Installer призначений лише для початкового завантаження (bootstrap) і не керує оркестрацією середовища виконання.

Підтримувані профілі розгортання:

1. Флот bare-metal.
2. Флот VPS/KVM.
3. Флот хмарних ВМ.
4. Гібридний флот (змішані класи нод під єдиним control plane).

## 2. Архітектурні інваріанти (Нульове відхилення)

Ці правила є обов'язковими для всіх нових модулів і всіх рефакторингів.

1. Жоден шар фасаду фреймворку не дозволений для поведінки виконання модулів.
2. Реєстрація та резолюція сервісів виконуються через [app/Support/Container.php](../../app/Support/Container.php).
3. Композиція маршрутів виконується через власні контракти маршрутизатора в [app/Http/Router.php](../../app/Http/Router.php) та [routes/api.php](../../routes/api.php).
4. Персистентність Control-Plane використовує PostgreSQL 18 через нативні з'єднання PDO `os`, `id` та `sd`.
5. Операції з БД тенантів Data-Plane використовують MariaDB 11.4+ через з'єднання PDO `payload`.
6. Пряме виконання на хості з контролерів/сервісів панелі заборонено (`shell_exec`, `exec`, `proc_open`, `passthru`, `system`).
7. Операції з хостом та середовищем виконання дозволені лише через типізовані транспортні контракти Agent з використанням [app/Services/Agent/NovusAgentClient.php](../../app/Services/Agent/NovusAgentClient.php).
8. Стилізація модулів Vue має використовувати токенізовані семантичні класи Tailwind та змінні теми з [config/themes.php](../../config/themes.php).
9. `<style scoped>` та інлайн `style="..."` у шаблонах Vue заборонені для поверхонь модулів.
10. Літерали i18n у шаблонах Vue заборонені; текст модуля має надходити зі словників `resources/locales/{ru,en,uk}`.

## 3. Проєкт домену бекенду (app/Modules/<Domain>/)

### 3.1 Обов'язкова структура директорій

Кожен модуль бекенд-домену мусить містити такі директорії та розподіл ролей:

1. `Http/` для обробників кінцевих точок / контролерів, зареєстрованих у контейнері.
2. `Services/` для бізнес-логіки домену та оркестрації.
3. `Providers/` для детермінованих файлів реєстрації в контейнері.
4. `Routes/` для маніфестів маршрутів домену.

Мінімальний каркас:

```text
app/Modules/<Domain>/
├── Http/
│   └── controllers.php
├── Services/
│   └── runtime_services.php
├── Providers/
│   ├── <domain>_core.php
│   └── <domain>_http.php
└── Routes/
    └── api.php
```

### 3.2 Вимоги до шару Http

1. API-контролери повинні успадковуватися від `App\Controllers\Api\ApiController`.
2. Успішні відповіді повинні використовувати детерміновані контракти-конверти (допоміжний метод контролера `ok` та/або `Response::json` з `{ ok: true, data: ... }`).
3. Відповіді про помилки повинні використовувати детерміновані контракти-конверти через допоміжні методи контролера для помилок (канонічна форма: `{ ok: false, error: { code, message } }` із полями сумісності, коли це вимагається поточною політикою міграції).
4. Довільні текстові корисні навантаження (payloads) для `error` заборонені для не-протокольних кінцевих точок.
5. Обробники маршрутів повинні бути тонкими адаптерами: нормалізація вхідних даних, перевірка прав доступу (permission gate), виклик сервісу, детерміноване відображення відповіді.

### 3.3 Політика винятків для протоколів (OAuth 2.0 / OIDC)

Правило детермінованого конверта має явний виняток для протоколів:

1. Кінцеві точки протоколу OAuth 2.0 / OIDC (наприклад, [app/Controllers/Api/OidcProtocolController.php](../../app/Controllers/Api/OidcProtocolController.php)) повинні відповідати формату помилок, сумісному з RFC 6749.
2. Дозволений формат корисного навантаження помилки протоколу:

```json
{
  "error": "invalid_request",
  "error_description": "Missing parameter: client_id"
}
```

3. Кінцеві точки протоколу під цим винятком повинні бути покриті спеціальними тестами протоколу, що доводять сумісну з RFC поведінку.
4. Цей виняток є вузьким і не повинен використовуватися повторно API панелей, які не стосуються протоколів.

### 3.4 Вимоги до рівня сервісів

1. Сервіси містять бізнес-логіку, переходи станів та межі транзакцій.
2. Сервіси не повинні створювати неформатовані об'єкти HTTP-виводу.
3. Сервіси не повинні викликати команди хоста напряму.
4. Зміни середовища виконання та хоста мають делегуватися типізованим методам `NovusAgentClient`.
5. Типи вхідних/вихідних даних мають бути детермінованими та придатними для аудиту.

### 3.5 Провайдери та ініціалізація (bootstrap wiring)

1. Реєстрації контейнерів модулів мають бути детермінованими та базуватися на файлах.
2. Реєстрації мають бути сумісними з [app/Support/Container.php](../../app/Support/Container.php).
3. Файли провайдерів модулів повинні завантажуватися через оркестрований порядок ініціалізації (див. [app/Modules/SystemCore/Providers/bootstrap_orchestrator.php](../../app/Modules/SystemCore/Providers/bootstrap_orchestrator.php)).
4. Порядок реєстрації провайдерів має бути доступним лише для додавання (append-only), якщо явний план міграції не передбачає іншого.

### 3.6 Маршрути та застосування прав доступу

1. Кожен модуль повинен мати ізольований за доменом маніфест маршрутів у `Routes/api.php`.
2. Маніфести маршрутів модулів повинні підключатися через [routes/api.php](../../routes/api.php), а не вбудовуватися довільно у незв'язані модулі.
3. Політика прав доступу повинна застосовуватися для кожного змінюваного ендпоінту.
4. Обов'язковий контракт іменування прав доступу: `platform.<domain>.<action>`.
5. Застосування прав доступу повинно виконуватися за допомогою контракту проміжного ПЗ (middleware) для прав доступу та/або допоміжних засобів захисту ApiController із детермінованою поведінкою заборони.

## 4. Архітектурний шаблон фронтенд-домену (resources/js/modules/<Domain>/)

### 4.1 Обов'язкова структура каталогів

```text
resources/js/modules/<Domain>/
├── views/
├── components/
├── api/
├── stores/
└── locales/
```

Якщо застарілий домен ще не містить усі каталоги, беклог міграції має відстежувати приведення до цієї структури.

### 4.2 Стандарти Vue SFC та UI

1. Vue 3 SFC з використанням script setup є режимом розробки за замовчуванням.
2. Використання `<style scoped>` заборонено.
3. Вбудовані атрибути стилів (inline style) заборонені для поверхонь модулів.
4. Токенізовані класи Tailwind та спільні змінні тем є обов'язковими.
5. Повторно використовуйте спільні компоненти вікон та оболонки для поведінки модальних вікон / вікон (наприклад, [resources/js/modules/Common/components/DesktopWindowWrapper.vue](../../resources/js/modules/Common/components/DesktopWindowWrapper.vue)).
6. Жорстко закодовані рядки, видимі користувачеві, у шаблонах заборонені.

### 4.3 Типізація фронтенд-транспорту

1. Кожен адаптер API модуля (`api/<domain>Api.ts`) має використовувати уніфікований типізований транспорт (`novusFetch<T>`, призначення якого визначено в WS-D.2).
2. Типізація відповідей API повинна моделювати детерміновані контракти сервера.
3. Обробка помилок автентификації/сесії має бути централізованою та не створювати нескінченних циклів.
4. Транспортні обгортки на рівні модулів, що обходять уніфіковане мапування помилок, заборонені.

## 5. Правила доступу Data-Plane проти Control-Plane

### 5.1 Використання бази даних control-plane

Використовуйте підключення PostgreSQL до control-plane (`os`, `id`, `sd`) для стану панелі та стану ідентифікації / служби підтримки (service-desk).

Приклад (control-plane):

```php
$os = $this->connections->connection('os');
$id = $this->connections->connection('id');
$sd = $this->connections->connection('sd');
```

### 5.2 Використання бази даних data-plane

Використовуйте підключення MariaDB для payload виключно для баз даних орендарів (tenant) / користувачів:

```php
$payload = $this->connections->connection('payload');
```

Ця межа є обов'язковою і не повинна обходитися шляхом прямого конструювання DSN у логіці модуля.

### 5.3 Типізовані помічники для запитів та ідентифікація

1. Використовуйте [app/Services/Database/DatabaseHelper.php](../../app/Services/Database/DatabaseHelper.php) для нормалізації параметрів та безпечного мапінгу JSON/JSONB.
2. Використовуйте ідентифікатори UUIDv7 через [app/Support/UuidV7.php](../../app/Support/UuidV7.php) для кореляції сутностей / запитів, де контракти модулів вимагають згенерованих ідентифікаторів.
3. Логіка модуля повинна розділяти SQL-концерни control-plane та data-plane за допомогою явного призначення підключення.

## 6. Оркестрація хоста та правила транспорту

### 6.1 Дозволений шлях операцій на хості

1. Панель отримує намір через автентифікований API-ендпоїнт.
2. Панель валідує права IAM/OIM.
3. Панель мапує намір у типізований Agent RPC через `NovusAgentClient`.
4. Агент виконує локальну для хоста операцію та повертає типізований результат.
5. Панель мапує результат у детермінований контракт відповіді API.

### 6.2 Заборонені патерни в модулях панелі

Усередині контролерів/сервісів панелі заборонено таке:

1. `shell_exec`, `exec`, `proc_open`, `passthru`, `system`.
2. Прямий доступ до `docker.sock`.
3. Володіння локальним PTY у середовищі виконання панелі.
4. Оркестрація команд на рівні root із HTTP-шляхів панелі.

Борг сумісності, виявлений у застарілих інтерфейсах, не є прецедентом для нового коду.

## 7. Забезпечення виконання контрактів та шлюзи якості

### 7.1 Шлюзи валідації

Забезпечення якості WS-D базується на наявних та запланованих перевірках:

1. перевірки цілісності посилань у документації.
2. перевірки швидкого пайплайну якості.
3. скрипт захисту контрактів модулів: [tools/quality/module_contract_check.php](../../tools/quality/module_contract_check.php).

### 7.2 Критерії збою CI

Зміна модуля повинна призводити до збою CI, якщо виконується будь-яка з умов:

1. Непротокольний ендпоінт API повертає недетерміновану структуру помилки.
2. У контролерах/сервісах модуля виявлено заборонений патерн host-exec.
3. Vue-шаблони модуля містять `<style scoped>` або інлайнові атрибути стилів.
4. Vue-шаблони модуля містять захардкоджені видимі користувачеві літерали замість ключів i18n.
5. Зміни поверхні маршрутів не узгоджені з маніфестами доменних маршрутів та політикою дозволів.

### 7.3 Обов'язкові перевірки для WS-D.1 та пізніших версій

Запускати та підтримувати зеленими:

1. `php tools/quality/docs_link_check.php`
2. `npm run quality:fast`

## 8. Еталонні реалізації та базова лінія аудиту

### 8.1 Еталонна реалізація бекенду

Еталонний модуль: [app/Modules/Databases](../../app/Modules/Databases)

Вимоги аудиту:

1. Явні межі з'єднань.
2. Реєстрація на основі контейнера.
3. Володіння маніфестом доменних маршрутів.
4. Детермінований мапінг контрактів API.

### 8.2 Золотий еталон фронтенду

Еталонний модуль: [resources/js/modules/Services](../../resources/js/modules/Services)

Очікування від аудиту:

1. Ізоляція компонентів за доменами.
2. Використання токенів Tailwind та узгодженість тем.
3. Інтеграція зі спільною оболонкою/вікном (shell/window).
4. Прогресивна конвергенція до повного контракту макету модуля.

## 9. Процедура впровадження

1. Створення нового модуля повинно починатися з цієї специфікації.
2. Плани рефакторингу існуючих модулів повинні посилатися на цю специфікацію в обсязі завдань.
3. Будь-який виняток вимагає явного запису архітектурного рішення (architecture decision record) у `docs/dev` із зазначенням відповідальної особи та терміну дії.
4. У разі конфлікту між цим документом і будь-яким старішим керівництвом, цей документ є пріоритетним для архітектури модулів.
