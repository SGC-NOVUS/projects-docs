# СПЕЦИФІКАЦІЯ МОДУЛЯ

Статус: нормативний
Власник: Panel Core Engineering
Обсяг: архітектура модуля panel-core
Останнє оновлення: 2026-09-24
Якорі: [AGENTS.md](../../AGENTS.md), [ECOSYSTEM_MANIFEST.md](../../ECOSYSTEM_MANIFEST.md), [Master Plan WS-D](../dev/MASTER_PLAN_PANEL_ENTERPRISE_AAA_2026-09-23.md)

## 1. Призначення та область застосування парку

Ця специфікація є Золотим стандартом для проєктування, аудиту та рефакторингу модулів у NOVUS-OS Panel.

NOVUS-OS є корпоративною багатонодовою Control-Plane для:

1. Віртуальної інфраструктури (VPS та хмарні ноди).
2. Фізичної інфраструктури (виділені сервери / bare-metal).
3. Оркестрації середовища виконання та управління життєвим циклом.
4. Моніторингу сервісів та спостережуваності за станом хостів/сервісів.
5. Робіт із ServiceDesk та управління інцидентами.
6. Вебсайтів (Nginx, PHP-FPM, життєвий цикл SSL).
7. Ізоляції баз даних та операцій з базами даних тенантів.
8. Резервного копіювання та операцій на платформі.

Модель топології:

1. Panel є control-plane оркестратором (політика, намір, стан, API-контракт).
2. Agent є фоновим процесом (демоном) execution-plane на керованих нодах.
3. Installer призначений виключно для початкового завантаження (bootstrap) і не керує оркестрацією середовища виконання.

Підтримувані профілі розгортання:

1. Парк bare-metal сервери.
2. Парк VPS/KVM.
3. Парк хмарних віртуальних машин.
4. Гібридний парк (змішані класи нод під єдиною control plane).

## 2. Архітектурні інваріанти (Нульове відхилення)

Ці правила є обов'язковими для всіх нових модулів і всіх рефакторингів.

1. Жодні фасадні шари фреймворку не дозволені для поведінки середовища виконання модулів.
2. Реєстрація та резолюція сервісів виконуються через [app/Support/Container.php](../../app/Support/Container.php).
3. Композиція маршрутів виконується через власні контракти маршрутизатора в [app/Http/Router.php](../../app/Http/Router.php) та [routes/api.php](../../routes/api.php).
4. Персистентність Control-Plane використовує PostgreSQL 18 через нативні з'єднання PDO `os`, `id` та `sd`.
5. Операції з БД тенантів Data-Plane використовують MariaDB 11.4+ через з'єднання PDO `payload`.
6. Пряме виконання на хості з контролерів/сервісів панелі заборонено (`shell_exec`, `exec`, `proc_open`, `passthru`, `system`).
7. Операції на хості та в середовищі виконання дозволені лише через типізовані транспортні контракти Agent з використанням [app/Services/Agent/NovusAgentClient.php](../../app/Services/Agent/NovusAgentClient.php).
8. Стилізація модулів Vue повинна використовувати токенізовані семантичні класи Tailwind та змінні теми з [config/themes.php](../../config/themes.php).
9. `<style scoped>` та інлайн `style="..."` у шаблонах Vue заборонені для інтерфейсів модулів.
10. Літерали i18n у шаблонах Vue заборонені; текст модуля має надходити зі словників `resources/locales/{ru,en,uk}`.

## 3. Проєкт домену бекенду (app/Modules/<Domain>/)

### 3.1 Обов'язкова структура каталогів

Кожен модуль бекенд-домену повинен містити такі каталоги та розподіл ролей:

1. `Http/` для обробників кінцевих точок / контролерів, зареєстрованих у контейнері.
2. `Services/` для бізнес-логіки домену та оркестрації.
3. `Providers/` для детермінованих файлів реєстрації в контейнері.
4. `Routes/` для маніфестів маршрутів домену.

Мінімальний каркас:

```text
app/Modules/<Domain>/
├── Http/
│   └── controllers.php
├── Services/
│   └── runtime_services.php
├── Providers/
│   ├── <domain>_core.php
│   └── <domain>_http.php
└── Routes/
    └── api.php
```

### 3.2 Вимоги до шару Http

1. API-контролери повинні успадковуватися від `App\Controllers\Api\ApiController`.
2. Успішні відповіді повинні використовувати детерміновані контракти-конверти (допоміжний метод контролера `ok` та/або `Response::json` з `{ ok: true, data: ... }`).
3. Відповіді про помилки повинні використовувати детерміновані контракти-конверти за допомогою допоміжних методів помилок контролера (канонічна форма: `{ ok: false, error: { code, message } }` із полями сумісності, коли це вимагається поточною політикою міграції).
4. Корисні дані `error` у вигляді довільних рядків заборонені для кінцевих точок, що не належать до протокольних.
5. Обробники маршрутів мають бути тонкими адаптерами: нормалізація вхідних даних, перевірка прав доступу, виклік сервісу, детерміноване мапування відповідей.

### 3.3 Політика винятків для протоколів (OAuth 2.0 / OIDC)

Правило детермінистичного конверта має явний виняток для протоколів:

1. Кінцеві точки протоколів OAuth 2.0 / OIDC (наприклад, [app/Controllers/Api/OidcProtocolController.php](../../app/Controllers/Api/OidcProtocolController.php)) мають відповідати формату помилок, сумісному з RFC 6749.
2. Дозволений формат корисного навантаження помилки протоколу:

```json
{
  "error": "invalid_request",
  "error_description": "Missing parameter: client_id"
}
```

3. Кінцеві точки протоколів, на які поширюється цей виняток, повинні бути покриті спеціальними тестами протоколів, що підтверджують поведінку, сумісну з RFC.
4. Цей виняток є вузькоспеціалізованим і не повинен використовуватися повторно API не протокольних панелей.

### 3.4 Вимоги до рівня сервісів

1. Сервіси містять бізнес-логіку, переходи станів та межі транзакцій.
2. Сервіси не повинні створювати сирі об'єкти виводу HTTP.
3. Сервіси не повинні викликати команди хоста безпосередньо.
4. Зміни середовища виконання та хоста мають делегуватися типізованим методам `NovusAgentClient`.
5. Типи вводу/виводу мають бути детермінованими та придатними для аудитів.

### 3.5 Providers and bootstrap wiring

1. Реєстрації контейнерів модулів мають бути детермінованими та базуватися на файлах.
2. Реєстрації повинні бути сумісними з [app/Support/Container.php](../../app/Support/Container.php).
3. Файли провайдерів модулів мають завантажуватися через оркестрований порядок ініціалізації (див. [app/Modules/SystemCore/Providers/bootstrap_orchestrator.php](../../app/Modules/SystemCore/Providers/bootstrap_orchestrator.php)).
4. Порядок реєстрації провайдерів має бути виключно додавальним (append-only), якщо інше не передбачено явним планом міграції.

### 3.6 Routes and permission enforcement

1. Кожен модуль повинен мати власний доменно-ізольований маніфест маршрутів у `Routes/api.php`.
2. Маніфести маршрутів модулів повинні підключатися через [routes/api.php](../../routes/api.php), а не вбудовуватися хаотично в непов'язані модулі.
3. Політика прав доступу повинна застосовуватися для кожного змінюваного (mutable) ендпоінту.
4. Обов'язковий контракт іменування прав доступу: `platform.<domain>.<action>`.
5. Застосування прав доступу має реалізуватися через контракт проміжного ПЗ (middleware) прав доступу та/або допоміжні засоби захисту ApiController із детермінованою поведінкою відмови.

## 4. Архітектурний план домену frontend (resources/js/modules/<Domain>/)

### 4.1 Обов'язкова структура каталогів

```text
resources/js/modules/<Domain>/
├── views/
├── components/
├── api/
├── stores/
└── locales/
```

Якщо застарілий домен ще не містить усіх каталогів, беклог міграції має відстежувати приведення до цієї структури.

### 4.2 Стандарти Vue SFC та UI

1. Vue 3 SFC з використанням script setup є режимом написання за замовчуванням.
2. Використання `<style scoped>` заборонено.
3. Атрибути вбудованих стилів (inline style) заборонені для поверхонь модулів.
4. Токенізовані класи Tailwind та спільні змінні тем є обов'язковими.
5. Повторно використовуйте спільні компоненти вікон та оболонки для поведінки модальних вікон / вікон (наприклад, [resources/js/modules/Common/components/DesktopWindowWrapper.vue](../../resources/js/modules/Common/components/DesktopWindowWrapper.vue)).
6. Жорстко закодовані рядки, видимі користувачеві, у шаблонах заборонені.

### 4.3 Типізація транспорту frontend

1. Кожен адаптер API модуля (`api/<domain>Api.ts`) має використовувати уніфікований типізований транспорт (ціль `novusFetch<T>`, визначена WS-D.2).
2. Типізація відповідей API повинна моделювати детерміновані контракти сервера.
3. Обробка помилок автентифікації/сесії має бути централізованою та не створювати цикли.
4. Транспортні обгортки на рівні модулів, які обходять уніфіковане мапування помилок, заборонені.

## 5. Правила доступу Data-Plane проти Control-Plane

### 5.1 Використання бази даних Control-plane

Використовуйте підключення PostgreSQL для control-plane (`os`, `id`, `sd`) для стану панелі та стану ідентифікації / service-desk.

Приклад (control-plane):

```php
$os = $this->connections->connection('os');
$id = $this->connections->connection('id');
$sd = $this->connections->connection('sd');
```

### 5.2 Використання бази даних Data-plane

Використовуйте підключення MariaDB для корисного навантаження (payload) тільки для баз даних орендарів/користувачів:

```php
$payload = $this->connections->connection('payload');
```

Ця межа є обов'язковою і не повинна обходитися шляхом прямого конструювання DSN у логіці модуля.

### 5.3 Типізовані помічники для запитів та ідентифікація

1. Використовуйте [app/Services/Database/DatabaseHelper.php](../../app/Services/Database/DatabaseHelper.php) для нормалізації параметрів та безпечного мапінгу JSON/JSONB.
2. Використовуйте ідентифікатори UUIDv7 через [app/Support/UuidV7.php](../../app/Support/UuidV7.php) для кореляції сутностей/запитів, де контракти модулів вимагають згенерованих ідентифікаторів.
3. Логіка модуля повинна розділяти SQL-запити control-plane та data-plane за допомогою явного призначення підключення.

## 6. Оркестрація хоста та правила транспорту

### 6.1 Дозволений шлях операцій хоста

1. Panel отримує намір через автентифіковану кінцеву точку API.
2. Panel перевіряє дозволи IAM/OIM.
3. Panel зіставляє намір із типізованим Agent RPC через `NovusAgentClient`.
4. Agent виконує локальну для хоста операцію та повертає типізований результат.
5. Panel зіставляє результат із детермінованим контрактом відповіді API.

### 6.2 Заборонені патерни в модулях panel

Усередині контролерів/сервісів panel заборонено таке:

1. `shell_exec`, `exec`, `proc_open`, `passthru`, `system`.
2. Прямий доступ до `docker.sock`.
3. Володіння локальним PTY в середовищі виконання panel.
4. Оркестрація команд кореневого рівня (root-level) з HTTP-шляхів panel.

Борг сумісності, виявлений у застарілих інтерфейсах, не є прецедентом для нового коду.

## 7. Дотримання контрактів та шлюзи якості

### 7.1 Шлюзи валідації

Забезпечення якості WS-D базується на наявних і запланованих перевірках:

1. перевірки цілісності посилань у документації;
2. перевірки швидкого конвеєра якості;
3. скрипт захисту контракту модуля: [tools/quality/module_contract_check.php](../../tools/quality/module_contract_check.php).

### 7.2 Критерії збою CI

Зміна модуля повинна призвести до збою CI, якщо виконується хоча б одна умова:

1. Непротокольний API endpoint повертає недетерміновану форму помилки.
2. У контролерах/сервісах модуля виявлено заборонений патерн host-exec.
3. Vue-шаблони модуля містять `<style scoped>` або вбудовані атрибути стилів (inline style).
4. Vue-шаблони модуля містять жорстко закодовані літерали для користувача замість i18n-ключів.
5. Зміни поверхні маршрутів не узгоджені з маніфестами маршрутів домену та політикою прав доступу.

### 7.3 Обов'язкові перевірки для WS-D.1 і пізніших версій

Запускайте та підтримуйте в зеленому стані (успішними):

1. `php tools/quality/docs_link_check.php`
2. `npm run quality:fast`

## 8. Еталонні посилання та базис аудиту

### 8.1 Еталон бекенду

Еталонний модуль: [app/Modules/Databases](../../app/Modules/Databases)

Очікування від аудиту:

1. Експліцитні межі з'єднань.
2. Реєстрація на основі контейнера.
3. Володіння маніфестом маршрутів домену.
4. Детерміноване мапінг-контракту API.

### 8.2 Золотий еталон фронтенду

Еталонний модуль: [resources/js/modules/Services](../../resources/js/modules/Services)

Вимоги до аутентичності:

1. Ізоляція компонентів за доменами.
2. Використання токенів Tailwind та узгодженість із темою.
3. Інтеграція зі спільною оболонкою / вікном.
4. Поступова збіжність до повного контракту макета модуля.

## 9. Процедура впровадження

1. Створення нового модуля має починатися з цієї специфікації.
2. Плани рефакторингу існуючих модулів повинні посилатися на цю специфікацію в обсязі завдання.
3. Будь-який виняток потребує явного запису про архітектурне рішення в `docs/dev` із зазначенням власника та терміну дії.
4. Якщо цей документ суперечить будь-якому старішому керівництву, цей документ є авторитетним щодо архітектури модулів.
