# Маніфест екосистеми NOVUS-OS

**Статус:** нормативний міжрепозиторний архітектурний контракт  
**Область застосування:** `panel-core`, `agent-core` та `installer`  
**Канонічне джерело:** цей документ створено у `panel-core/docs/architecture/` та синхронізовано досліввно до кореня кожного репозиторію.

## 1. Бачення продукту та архітектурна філософія

NOVUS-OS — це Web-OS для керування керованою інфраструктурою через єдину контрольну поверхню, нативну для браузера. Вона замінює фрагментовані зовнішні інструменти адміністрування, такі як WinSCP та PuTTY, на робочі процеси з перевіркою прав: керування файлами, доступ до термінала, життєвий цикл служб та контейнерів, мережі, резервні копії, вебсайти, бази даних, телеметрія та адміністрування безпеки.

Продукт має два взаємодоповнювальні режими інтерфейсу користувача:

| Режим | Призначення |
| --- | --- |
| **Dashboard** | Швидкий операційний огляд: стан здоров'я, телеметрія, сповіщення, черги, інвентаризація та високочастотні дії. |
| **WebDesktop** | Постійний робочий простір з кількома інструментами для автентифікованих операторів, з маршрутизованими панелями для файлів, терміналів, екземплярів, вебсайтів, баз даних та адміністрування. |

Фронтенд є браузерним додатком з оболонкою, хеш-маршрутизацією, ледаче завантажуваними функціональними модулями Vue, спільними службами середовища виконання UI, i18n та підтримкою життєвого циклу PWA. PWA є властивістю доставки та стійкості панелі UI; він ніколи не передає повноваження хоста браузеру.

Архітектура дотримується суворого розділення на Control-Plane, Data-Plane та завантаження (bootstrap):

1. Панель вирішує, *хто може що запитувати*, зберігає намір та стан, а також представляє результати.
2. Agent виконує привілейовану локальну роботу на хості лише після автентифікованого транспортного запиту.
3. Installer готує хост один раз, передає постійне володіння Panel та Agent, а потім видаляє власну завантажувальну поверхню.

## 2. Матриця тристоронніх меж

| Репозиторій / роль | Дозволено та належить | Суворо заборонено |
| --- | --- | --- |
| **`panel-core` - Мозок / Control-Plane** | PHP-додаток, Vue/PWA UI, стан продукту на базі PostgreSQL, оцінка політик IAM/OIM, маршрутизація API, оркестрація, журнали аутентифікації/аудиту, наміри команд, метадані з'єднань, бізнес-правила та представлення результатів Agent. | Пряме адміністрування хоста на рівні root; пряме використання Docker socket; пряма мутація файлової системи хоста; володіння локальним PTY; вбудовування привілейованих робочих процесів Bash або `sudo` як заміна Agent RPC. Новий код повинен використовувати фасад Agent та типизовані транспортні контракти. |
| **`agent-core` - Руки і ноги / Data-Plane** | Довготривалий демон на Go, автентифіковані службі gRPC, зонди хоста, операції з Docker та системою, примусове застосування VFS, операції з файловою системою контейнерів, потокове передавання PTY, збір телеметрії та керування канонічними томами екземплярів. | Веб-інтерфейс, сеансові потоки / потоки автентифікації браузера, рішення щодо політик IAM/OIM продукту, стан control-plane PostgreSQL, оркестрація бізнес-процесів або пряме зв'язування з внутрішніми компонентами Panel та схемою бази даних. |
| **`installer` - Ефемерний бутстрапер** | Перевірка перед запуском виключно для root, встановлення залежностей, завантаження та перевірка версій артефактів випусків, початкове розгортання / конфігурація, початкові секрети / маніфест бутстрапу, прогрес встановлення в терміналі та перевірка працездатності після встановлення. | Перетворення на постійну службу, виконання ролі середовища виконання Panel, збереження облікових даних користувача після завершення, реалізація поточних операцій життєвого циклу хоста або залишення на успішному робочому хості. |

The Installer володіє лише тимчасовим протоколом налаштування: вбудованим інтерфейсом з обмеженим доступом за токеном, `POST /api/setup`, та `GET /api/stream` для фреймів текстового стану та двійкового виведення PTY. Це не є каналом керування Panel-to-Agent і не надає браузеру жодних постійних повноважень хоста.

### Володіння доменами Panel

`panel-core/app/Modules` є межею додатку Panel. Його доменами є `SystemCore`, `SecurityIAM`, `RuntimeInstances`, `WebsitesVHosts`, `Databases`, `MonitoringTelemetry`, `FilesVFS`, `AgentTransportFederation` та `PlatformOps`.

`routes/api.php` формує публічний HTTP-контракт із файлів маршрутів цих модулів. Контролери є HTTP/перетворювачами дозволів (адаптерами); сервіси володіють бізнес-логікою; `NovusAgentClient` та його прямі/федеровані драйвери є канонічною поверхнею інтеграції Panel-to-Agent.

### Сумісність боргу не є авторитетом

Панель містить застарілі шляхи локального доступу до оболонки / Docker, зокрема `DashboardController` та локальний резервний механізм логів контейнера. Вони є технічним боргом сумісності, а не прецедентом. Їх заборонено копіювати, розширювати чи використовувати для нової функціональності. Заміна повинна зберігати зовнішній HTTP-контракт із перенесенням виконання на межу транспорту Agent.

## 3. Договор міжпроцесної взаємодії

Комунікація між Panel та Agent базується на gRPC. Авторитетні визначення protobuf знаходяться в `agent-core/proto/`; Panel використовує «сирий» кодек protobuf та транспортні драйвери виключно для реалізації цих контрактів. Поточний gRPC-сервер реєструє `NovusAgent`, `NovusRuntimeSurface`, `InstanceService` та `BackupService`.

| Аспект | Контракт |
| --- | --- |
| Транспорт | TLS є обов'язковим для gRPC-слухача Agent. Panel обирає прямий або федеративний драйвер на основі метаданих вузла; прямі операції виконання працюють переважно через gRPC. Резервний HTTP-варіант, якщо його явно налаштовано для сумісності, не є контрактом для нових функцій. |
| Автентифікація | Кожен привілейований запит містить `x-panel-uuid`, `x-request-timestamp` та `x-signature`. Agent перевіряє HMAC-SHA256 для корисного навантаження protobuf із наступним часовою міткою, стандартним вікном годинника у 15 секунд, блокуванням Panel, захистом від повтору (Replay Guard), лімітами запитів та логуванням аудиту безпеки перед виконанням роботи. Спарювання та стандартна перевірка працездатності gRPC є навмисними винятками без підпису. |
| Авторизація | Panel оцінює права IAM/OIM користувача перед видачею наміру. Agent забезпечує дотримання лише власної вузької межі операцій/області дії та ніколи не сприймає вхідні дані браузера як авторизацію. |
| Ідентифікація та кореляція | Запити використовують ідентифікатор вузла та UUID запиту. Журнали, події, помилки та підтвердження стану зберігають цей ідентифікатор кореляції по обидва боки межі. |
| Унарні операції | Інформація про хост, життєвий цикл контейнера, VFS, вебсайти, SSL, системні операції, операції резервного копіювання та запити телеметрії використовують типізовані повідомлення запиту/відповіді protobuf. Panel надсилає DSL для Agent, а не «сирі» корисні навантаження Docker API. |

| Server streams | Потоки сервера | Надання екземплярів і перебіг витягування контейнерів використовують типізовані серверні потоки; логи, телеметрія та інші безперервні виводи повинні відповідати обмеженим контрактам потоків, що скасовуються, і зберігати ідентифікатори кореляції (correlation ID). |
| Bidirectional PTY | Двонаправлений PTY | Введення/виведення термінала використовує фрейми `NovusAgent.PtyStream` (`open`, `input`, `resize`, `output`, `exit`, `error`). Agent дозволяє лише налаштовані шляхи до оболонки (shell paths) і запускає команди без інтерполяції оболонки. Браузер ніколи не відкриває неавтентифікований хостовий PTY; Panel авторизує та ретранслює сеанс користувача через контракт Agent. |

Жоден репозиторій не може незалежно змінювати назви сервісів protobuf, поля повідомлень, назви метаданих, правила підписання чи семантику потоків. Зміна контракту вимагає узгодженого вихідного коду, підтримки генерації/кодеків, місця виклику в Panel, обробника Agent та цілеспрямованих тестів сумісності в межах одного плану випуску.

## 4. Стандарт топології сховища та файлової системи

Канонічним фізичним коренем сховища для керованих персистентних даних є:

```text
/var/lib/novus/volumes/
├── games/      # Томи екземплярів ігрових серверів
├── service/    # Томи екземплярів додатків і сервісів
└── web/        # Томи вебсайтів і вебконтейнерів Docker
```

`/www/containers` є лише точкою входу для навігації, а не другим деревом сховища:

```text
/www/containers -> /var/lib/novus/volumes/web
```

Решта межі хоста складається з:

```text
/www/panel/                 # Розгорнутий додаток Panel, ніколи не є томом тенанта
/www/sites/                 # Класичні сайти на рівні хоста, незалежно ізольовані
/etc/novus/secrets/         # Секрети поза вебкоренем
/etc/novus/secrets/panel-novus.env
/etc/novus/agent.yaml       # Зашифрований стан сполучення Agent та головний секрет
/etc/novus/tls/             # Ключовий матеріал gRPC TLS для Agent
```

/etc/novus/manifest.json    # До довговічних метаданих ідентичності бутстрапа/хоста
```

Секрети повинні залишатися поза межами `/www/panel` та поза монтуваннями тенантів/контейнерів. Зокрема, конфігурація Panel для продуктивного середовища завантажується з `/etc/novus/secrets/panel-novus.env` з мінімальними дозволами, необхідними для служби Panel (`0640 www-data:www-data` у базовому встановлювачі); файл `.env` у каталозі `/www/panel` є порушенням безпеки. Стан агента, приватні ключі TLS, головні ключі (master keys), матеріали JWT та аудиторські записи встановлювача є секретами хоста і не повинні монтуватися в контейнери тенантів. Агент повинен резолвити шляхи томів через свої обмежені правила VFS/екземпляра та не повинен допускати обхід (traversal) між кореневими каталогами тенантів, файлами Panel або шляхами секретів.

### Поточні відхилення в реалізації

Нижче наведено зааудитовані факти, а не схвалення для нового коду:

| Поверхня | Поточний факт | Обов'язковий напрямок |
| --- | --- | --- |
| Виконання хоста Panel | Застарілі шляхи сумісності `DashboardController` та локальних логів усе ще викликають Docker/shell локально. | Зберегти зовнішній API, перенісши виконання на `NovusAgentClient` та типізований Agent RPC. |
| Політика Agent VFS | `internal/grpcserver/server.go` наразі конструює VFS з параметром `AllowedRoots: []string{"/"}`. Це зберігає доступ адміністратора хоста, але не примушує застосовувати стандарт обмежених томів (scoped-volume) для звичайної робочої рутини. | Розділити політику явним чином на `host_admin` та обмежені режими екземпляра/сайту/гри (instance/site/game); встановити для середовища виконання обмеження за замовчуванням до `/var/lib/novus/volumes/*` та перевірити обхід символічних посилань (symlink traversal). |

| Джерело контракту Agent | Живий сервер реєструє `BackupService`, тоді як зафіксовані у сховищі вихідні файли `.proto` не оголошують його; `NovusFileSystem` оголошено, але він не зареєстрований поточним коренем композиції сервера (composition root). | Узгодьте вихідні файли `.proto`, згенеровані заглушки, реєстрацію сервера, кодеки/місця викликів Panel та тести сумісності перед зміною будь-якої з поверхонь. |
| Допоміжний транспорт Agent | Поточний демон також запускає слухачі HTTP WebSocket-console та SSH/SFTP для сумісності. | Розглядайте їх як транспортні адаптери Agent, а не як другий інтерфейс користувача продукту чи рівень політик; зведе їхню аутентификацію та перевірки областей дії (scope) до межі gRPC. |
| Цілісність артефактів інсталятора | Інсталятор наразі перевіряє лише успішність завантаження, мінімальний розмір та читабельність архіву, але ще не примушує застосовувати контрольні суми релізів для кожного артефакту Panel та Agent. | Отримуйте метадані релізів із версіонуванням та вимагайте перевірки SHA-256 перед активацією артефакту. |
| Попередня перевірка інсталятора | Перевірка середовища виконання наразі обмежує лише порти `80` та `443`; генеральний план інсталятора вимагає перевірок на відповідність також для `8080` та `9443`. | Перевіряйте всі зовнішньо прив'язані порти bootstrap та Agent перед встановленням у виробничому середовищі, зберігаючи при цьому явну поведінку зниження версії для `--dev`. |
| Транспорт сеансу інсталятора | Тимчасовий сервер налаштування наразі прив'язується до `:8080`, видає 128-бітний токен URL та встановлює cookie `HttpOnly`/`SameSite=Strict` без атрибута `Secure`. | Зберігайте короткостроковий захист за токеном, обмежте доступ лише сеансом встановлення та завершіть заплановане посилення захисту cookie/транспорту, перш ніж вважати кінцеву точку безпечною для виробничого середовища. |

## 5. Автономні інструкції для ШІ

Перед виконанням будь-якого завдання агент ШІ повинен прочитати локальний для репозиторію `ECOSYSTEM_MANIFEST.md` і дотримуватися цих меж.

### Під час роботи в `panel-core`

- Реалізуйте лише політику продукту, персистентність, IAM/OIM, контракти API, сервіси, інтерфейс користувача та оркестрацію.
- Не додавайте `shell_exec`, `exec`, `system`, `sudo`, доступ до сокета Docker, кореневі команди (root commands), пряму модифікацію хостової VFS або довготривале володіння PTY.
- Виражайте наміри хоста через `NovusAgentClient` і межу драйвера на основі protobuf; зберігайте HTTP/OpenAPI контракти Panel під час міграції застарілого коду.
- Вважайте дані відповіді агента недовіреним вхідним транспортним потоком, доки вони не будуть валідовані та зіставлені з доменними об'єктами Panel.

### Під час роботи в `agent-core`

- Реалізуйте типізовані gRPC-обробники, валідацію підписаних запитів, захист від повторного відтворення (replay defense), локальне для хоста виконання, ізоляцію VFS (VFS containment), телеметрію та обробку потоків PTY.
- Не додавайте веб-інтерфейс, автентифікацію в браузері / реалізацію сесій, доступ до бази даних Panel або рушій бізнес-політик / політик IAM.
- Не розширюйте привілеї або кореневі каталоги файлової системи лише для того, щоб задовольнити запит на зручність від Panel; еволюціонуйте типізований контракт і валідацію разом.

### Під час роботи в `installer`

- Реалізуйте лише повторювані кроки перевірки перед запуском (preflight)/ініціалізації, отримання та перевірки релізу, початкову конфігурацію, телеметрію встановлення та фінальну перевірку працездатності.
- Зберігайте кожен побічний ефект ідемпотентним і робіть `--จdry-run` вільним від побічних ефектів.
- Завантажуйте скомпільовані/версіоновані артефакти релізів із затверджених джерел розповсюдження на GitHub; не виконуйте компіляцію і не станьте виробничим Control-Plane.
- У не-режимних (non-development), не-dry-run шляхах успіху визначайте поточний виконуваний файл за допомогою `os.Executable()` і видаляйте його після надсилання фінальної події завершення. Не виконуйте самовидалення у разі помилки, в режимі розробки або на шляхах dry-run.

### Правила між репозиторіями

- Не дублюйте повноваження іншого репозиторію, щоб уникнути змін в RPC або розгортанні.
- Не розголошуйте секрети, приватні ключі, сирі облікові дані або шляхи рівня хоста в корисних навантаженнях браузера, логах, телеметрії або файлах репозиторію.
- Зберігайте міграції та кроки встановлення/конфігурації ідемпотентними.
- Зміни, що перетинають межі, повинні оновлювати відповідний контракт, документацію, цільові тести та послідовність релізів одночасно.
