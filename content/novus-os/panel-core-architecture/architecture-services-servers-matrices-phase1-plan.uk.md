# Капітальний ремонт сервісів/серверів/матриць NOVUS-OS — План Фази 1

## Директива (як вимагається)

Виступайте в ролі Головного корпоративного архітектора та Провідного UI/UX-інженера. Підтвердьте отримання цієї директиви, ознайомтесь із довідковими матеріалами panel-main та надайте покроковий технічний план для Фази 1. Почніть реалізацію одразу після плану.

## Підтвердження

Директиву прийнято. Цей план Фази 1 базується на:
- поведінці домену panel-main (життєздатність вузлів, вибір розміщення, управління змінними та оркестрація створення серверів)
- поточній топології виконання panel-novus (орієнтована на екземпляри модель, пул мережевих каналів, таблиці профілів)
- поточних лімітах конверта agent-core (лише часткові cgroups для CPU/RAM)

## Архітектурний півот (2022-05-26)

Прийнято та застосовано півот до фази Пре-Фаза 1:
1. Реєстр вузлів перенесено з поведінки на основі плоских файлів на поведінку на основі БД у `panel_nodes`.
2. Канонічне сховище розподілу перенесено в `panel_node_allocations`, пов'язане з `panel_nodes.id`.
3. Застарілі файли стану JSON залишаються як резервний варіант сумісності / джерело імпорту під час переходу.

## Необхідні обмеження

1. Жодного прямого копіювання коду з panel-main.
2. Зберегти публічні API, які використовуються поточним фронтендом panel-novus та агентами.
3. Впровадити канонічну схему та сервіси зі зворотними сумісними шляхами резервного копіювання (fallback).
4. Застосувати жорсткі перевірки ресурсів, де ємність налаштована явно.

## Реконструйована логіка panel-main (Математична/Архітектурна)

1. Формула життєздатності вузла:
- effective_limit = base_capacity * (1 + overallocate_pct / 100)
- viable(resource) = (current_committed + requested) <= effective_limit

2. Політика вибору виділення (allocation):
- знайти вільні кандидати IP:port на цільовому вузлі
- виділений режим виключає адреси, які вже зайняті іншими прив'язками
- детермінований вибір першого доступного може замінити випадковий вибір для відтворюваності

3. Конвеєр провізіонінгу:
- визначити життєздатний вузел
- визначити виділення (allocation)
- перевірити змінні/правила
- зберегти сервер/екземпляр
- ініціювати створення середовища виконання

4. Керування змінними:
- зарезервовані ключі середовища заблоковані

- динамічні правила валідації застосовуються перед комітом

## Phase 1 Scope (This Wave)

1. Канонічна модель пулу вузлів у novus_os.
2. Канонічна таблиця виділень та служба розподільника (allocator service).
3. Жорсткі перевірки реєстру ресурсів із забороною на шляхах створення/запису ресурсів (create/resources-write paths).
4. Суворе поширення конверта обмежень виконання (runtime limits envelope) у корисне навантаження створення контейнера (container create payload).
5. Розширення прото в agent-core (адитивне, із збереженням зворотної сумісності).

## Step-by-Step Technical Plan

1. Основа схеми (Schema foundation):
- додати ідемпотентну міграцію для створення/оновлення `panel_nodes`
- додати ідемпотентну міграцію для створення/оновлення `allocations`
- заповнити `panel_nodes` на основі виявленого node_agent_id в таблицях часу виконання
- заповнити `allocations` з `panel_network_channels` для забезпечення безперервності переходу

2. Доменні служби (Domain services):
- додати `NodeResourceLedgerService` для обчислення використаних/віільних/лімітних ресурсів з урахуванням логіки надмірного виділення (overallocate math)
- додати `AllocationPoolService` для резервування першого доступного IP:port з `allocations`

3. Підключення конвеєра (Pipeline wiring):
- застосувати перевірки реєстру в `InstanceMutationService::create()`
- застосувати перевірки реєстру в `InstanceProfileService::saveResources()` із самовиключенням
- оновити `ProvisioningService`, щоб він надавав перевагу пулу `allocations` та повертався до застарілих `panel_network_channels`, коли канонічний пул не активний

4. Транспортування суворих обмежень (Strict limits transport):
- розширити корисне навантаження ініціалізації полями disk/swap/oom/pids
- розширити запит створення docker в agent-core / мапінг конфігурації хоста для примусового застосування cgroups/storage/pids там, де це підтримується

5. Розширення контракту (Contract expansion):
- додати адитивне повідомлення `ContainerHardwareLimits` у `agent-core/proto/novus.proto`
- додати необов'язковий конверт обмежень у `DockerManagerRequest` (без ламання RPC-змін)
- регенерувати `internal/gen/novus/v1/*.pb.go`

6. Перевірка (Verification):
- оновлення цільових модульних тестів panel-novus (построитель корисного навантаження)
- перевірки синтаксису/лінтування змінених PHP-файлів
- `go test ./...` та `go build ./...` в agent-core

7. Стратегія розгортання (Rollout posture):

- зберігати розподільник застарілих мережевих каналів як резервний шлях
- увімкнути канонічні виділення за наявністю даних, а не за переходом у день випуску (flag day cutover)

## Deliverables of Phase 1

1. Артефакти канонічної схеми (`panel_nodes`, `allocations`) з ідемпотентною міграцією.
2. Жорстка заборона у реєстрі ресурсів (hard-deny enforcement).
3. Сервіс розподільника першого доступного ресурсу та інтеграція забезпечення (provisioning).
4. Суворий конверт обмежень часу виконання, що передається наскрізно (end-to-end).
5. Адитивне оновлення контракту proto та згенеровані заглушки (stubs).
