# Перегляд служб/серверів/матриць NOVUS OS — План Фази 1

## Директива (за запитом)

Виступайте в ролі Головного корпоративного архітектора (Principal Enterprise Architect) та Провідного інженера з UI/UX. Підтвердьте цю директиву, ознайомтеся з довідковими матеріалами panel-main та надайте покроковий технічний план для Фази 1. Почніть реалізацію одразу після плану.

## Підтвердження

Директиву прийнято. Цей план Фази 1 базується на:
- доменній поведінці panel-main (життєздатність вузлів, вибір розподілу, керування змінними та оркестрація створення серверів)
- поточній топології виконання panel-novus (модель, орієнтована на екземпляри, пул мережевих каналів, таблиці профілів)
- поточних лімітах конверта agent-core (тільки часткові cgroups для CPU/RAM)

## Архітектурний поворот (2026-05-22)

Передфазовий поворот прийнято та застосовано:
1. Реєстр вузлів перенесено з поведінки «спочатку плоский файл» на поведінку «спочатку БД» у `panel_nodes`.
2. Канонічне сховище розподілу перенесено до `panel_node_allocations`, пов'язаного з `panel_nodes.id`.
3. Застарілі файли стану JSON залишаються як резервний варіант сумісності / джерело імпорту під час переходу.

## Non-Negotiable Constraints

1. Жодного прямого копіювання коду з panel-main.
2. Зберегти публічні API, які використовуються поточним фронтендом panel-novus та агентами.
3. Впровадити канонічну схему та сервіси зі шляхами резервного копіювання, сумісними у зворотний бік.
4. Застосовувати жорсткі перевірки ресурсів там, де ємність налаштована явно.

## panel-main Logic Reconstructed (Mathematical/Architectural)

1. Формула життєздатності вузла:
- effective_limit = base_capacity * (1 + overallocate_pct / 100)
- viable(resource) = (current_committed + requested) <= effective_limit

2. Політика вибору розподілу:
- знайти кандидатів вільних IP:port на цільовому вузлі
- виділений режим виключає адреси, які вже зайняті іншими прив'язками
- детермінований вибір першого доступного може замінити випадковий вибір задля відтворюваності

3. Форма конвеєра надання ресурсів:
- визначити життєздатний вузол
- визначити розподіл(ення)
- перевірити змінні/правила
- зберегти сервер/екземпляр
- надіслати запит на створення середовища виконання

4. Керування змінними:
- зарезервовані ключі середовища заблоковано
- динамічні правила перевірки застосовуються перед фіксацією (commit)

## Phase 1 Scope (This Wave)

1. Канонічна модель пулу вузлів у novus_os.
2. Канонічна таблиця виділень та сервіс розподілу.
3. Жорсткі перевірки реєстру ресурсів із забороною на шляхах create/resources-write.
4. Поширення конверта суворих обмежень часу виконання у корисне навантаження створення контейнера.
5. Розширення proto в agent-core (адитивне, зі збереженням сумісності назад).

## Step-by-Step Technical Plan

1. Schema foundation:
- додати ідемпотентну міграцію для створення/оновлення `panel_nodes`
- додати ідемпотентну міграцію для створення/оновлення `allocations`
- заповнити `panel_nodes` на основі виявленого node_agent_id в таблицях runtime
- заповнити `allocations` з `panel_network_channels` для забезпечення безперервності переходу

2. Domain services:
- додати `NodeResourceLedgerService` для обчислення використаних/віільних/лімітних ресурсів з урахуванням логіки overcommit
- додати `AllocationPoolService` для резервування першої доступної комбінації IP:port з `allocations`

3. Pipeline wiring:
- застосувати перевірки реєстру в `InstanceMutationService::create()`
- застосувати перевірки реєстру в `InstanceProfileService::saveResources()` з виключенням себе
- оновити `ProvisioningService`, щоб він надавав перевагу пулу `allocations` і повертався до застарілих `panel_network_channels`, коли канонічний пул не активний

4. Strict limits transport:
- розширити корисне навантаження провізінінгу полями disk/swap/oom/pids
- розширити запит створення docker в agent-core / мапінг конфігурації хоста для примусового застосування cgroups/storage/pids там, де це підтримується

5. Contract expansion:
- додати адитивне повідомлення `ContainerHardwareLimits` у `agent-core/proto/novus.proto`
- приєднати опціональний конверт лімітів у `DockerManagerRequest` (без ламання змін RPC)
- перегенерувати `internal/gen/novus/v1/*.pb.go`

6. Verification:
- цільові оновлення модульних тестів panel-novus (побудовник корисного навантаження)
- перевірки синтаксису/лінту у змінених файлах PHP
- `go test ./...` та `go build ./...` в agent-core

7. Rollout posture:

- зберегти розподілювач застарілих мережевих каналів як резервний шлях
- увімкнути канонічні виділення за наявністю даних, а не за переходом у день випуску (flag day cutover)

## Deliverables of Phase 1

1. Артефакти канонічної схеми (`panel_nodes`, `allocations`) з ідемпотентною міграцією.
2. Жорстка заборона у реєстрі ресурсів (resource ledger hard-deny enforcement).
3. Служба розподілу першого доступного та інтеграція забезпечення (provisioning).
4. Суворий конверт обмежень виконання, що передається наскрізно (end-to-end).
5. Адитивне оновлення контракту proto та регенеровані заглушки.
